> **一句话**：把 10 个微服务、40 个 Controller、218 个接口变成一张可检索的图，
> 用户说一句中文，系统自己定位接口、追问缺失参数、带着用户的身份真实执行。

## 一、这次更新做了什么

### 1.1 能力拆成四层

| 层 | 做什么 | 入口 |
|---|---|---|
| ① 建图 | 静态扫描 Java 源码，把「服务 → 模块 → 接口 → 参数」抽成图；也可从各服务 `/v3/api-docs` 重建真实 schema | `scripts/build-arch-graph.py`、`ArchGraphService.rebuild()`、`OpenApiCollector` |
| ② 路由 | 中文口语 → 候选接口（默认 8 个，带分数和命中词） | `ArchGraphService.search()`、`GraphText` |
| ③ 抽槽 | 候选接口 + 用户原话交给千问（Dify），返回「选了哪个 + 填了哪些参数 + 缺什么」 | `SlotFiller`、`ActionSession` |
| ④ 执行 | 五道闸校验 → 经网关透传用户 JWT → 返回结构化结果 | `ActionExecutor`、`ActionAssistantService`、`ActionController` |

**关键设计**：执行这一步**不制造身份**。ai-service 把用户原来的 `Authorization`
一路带到网关，下游服务看到的仍然是这个用户 —— 越权判定全部由下游既有的鉴权逻辑负责，
AI 层不新增一套权限模型。

### 1.4 联调时发现并修掉的三个问题

这三条都不是「新功能」，是**验证阶段发现的真实缺陷**，值得单独记一笔。

**① 8 个服务间接口被误判成「可执行」**

扫描器原来只看类名里有没有 `Internal`。但 `sales` / `distribution` / `trace` 有 8 个接口
是把 `/internal` 写在**方法级注解**上的，例如：

```java
@GetMapping("/internal/products")   // 类名是 SalesQueryController，干干净净
public Result<?> products(...)
```

类名不含 `internal` → 标记成 `false` → 对任何登录用户开放。而这些接口内部是不做业务权限
校验的（它们默认调用方可信）。

修法三层兜底：

1. 扫描器改为按**路径段**判定（`is_internal_path()`）；
2. `ApiOperation` 构造器再按 `path` / `gatewayPath` 纠正一次 —— 种子、运行时 OpenAPI、
   手写测试数据三者结论一致；
3. `executable` 一律问 `ActionExecutor`，不再各算各的。

效果：`internalCount` 45 → **53**，`/sales/internal/*` 从检索第二名掉到 0.43 并被标 `exec=False`。

**② 路径黑名单用 `startsWith` 会漏**

黑名单写的是 `/internal`，而 `/sales/internal/products` 并不以它开头。
现在改为「开头 **或** 中间某个完整路径段」匹配，`/administration/list` 这种只是字符串像的
不会被误杀；同时 `path` 和 `gatewayPath` 都看 —— ai-service 自己的接口在本地是
`/graph/stats`，只有拼上网关前缀才落在 `/ai/` 下，不看 `gatewayPath` 就拦不住
（拦不住意味着对话接口能被自己无限套娃调用）。

**③ 调试接口的 `executable` 在撒谎**

`/ai/graph/search` 原来自己拼 `enabled && !internal`，于是 `POST /farms`、
`/ai/graph/stats` 都显示「可执行」，调试时会被带偏。现在直接问执行器，
并多返回一个 `denyReason` 字段说明拒绝原因。

**另外两处体验修正**：降级（连不上千问）产生的回答前面统一挂一句
「这是按关键词匹配选的，可能不是你想要的」；错误文案的脱敏从只抹 IP 补到抹 `localhost`，
并截断到 200 字。

## 二、接口总览

### 2.1 五个接口

| 方法 | 网关路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/api/v1/ai/action/chat` | 发一句话，返回结构化结果（多轮补参数） | JWT + `X-User-Id` |
| POST | `/api/v1/ai/action/confirm` | 写操作二次确认 | JWT + `X-User-Id` |
| GET | `/api/v1/ai/graph/stats` | 图谱规模、各服务接口数 | JWT + `X-User-Id` |
| GET | `/api/v1/ai/graph/search` | 检索调试：看候选、分数、命中词、是否可执行 | JWT + `X-User-Id` |
| POST | `/api/v1/ai/admin/graph/rebuild` | 从各服务 `/v3/api-docs` 重建图谱 | JWT + `X-User-Id` + **SUPERVISOR/ADMIN** |

**鉴权怎么来的**：网关 `AuthGlobalFilter` 验完 JWT 后注入 `X-User-Id` / `X-User-Role`。
ai-service 再次校验这两个头，因为 8089 可能在容器网络内被直连 —— 只靠网关那一层不够。
`/ai/admin/**` 由 `AdminRoleInterceptor` 拦截（`ai.security.role-check-enabled=false` 可在本地关掉）。

**本地直连调试**（不起网关时）自己补头即可：

```bash
curl -H "X-User-Id: 1" -H "Authorization: Bearer dev-token" \
     http://localhost:8089/ai/graph/stats
```

### 2.2 统一响应信封

所有接口返回同一层外壳（`Result<T>`）：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { },
  "traceId": "2db0825d12a94aa29e0ffc5b1480e144",
  "timestamp": 1795072711949
}
```

### 2.3 错误码

| code | 触发条件 |
|---|---|
| 200 | 请求处理完成。**注意**：业务失败也是 200，看 `data.phase` |
| 400 | 缺 `q` / 缺 `conversationId` |
| 401 | 没带 `X-User-Id`（`请先登录`）或没带 `Authorization`（`缺少访问令牌`） |
| 403 | `/ai/admin/**` 角色不是 SUPERVISOR/ADMIN |
| 503 | `ai.action.enabled` 或 `ai.graph.enabled` 被关掉 |

**为什么不把业务失败做成非 200**：一次操作的结果分「我理解成了什么」「还缺什么」
「执行成功没有」三段，其中第二段是正常流程而不是错误。用 `phase` 表达比堆 HTTP 状态码清楚。

## 三、接口详情

### 3.1 POST `/api/v1/ai/action/chat`

把一句话翻译成接口调用。**多轮**：同一个 `conversationId` 会复用上下文。

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `text` | string | 是 | 用户这句话，上限 500 字。**字段名是 `text`，不是 `message`** |
| `conversationId` | string | 否 | 上一轮返回的会话 id；为空表示新会话 |
| `reset` | boolean | 否 | `true` 表示丢掉上下文重开（用户说「算了，换个事」） |

> 字段名写错的代价：Jackson 会静默忽略未知字段，接口返回「请输入你想做的事」，
> 看起来像检索失败。排查时先看一眼这里。

```bash
curl -X POST 'http://localhost:8089/ai/action/chat' \
  -H 'X-User-Id: 1' \
  -H 'Authorization: Bearer <用户JWT>' \
  -H 'Content-Type: application/json' \
  -d '{"text":"查看产地检疫证明"}'
```

#### `phase` 状态机

| phase | 含义 | 前端该做什么 |
|---|---|---|
| `UNSUPPORTED` | 没找到能对应这句话的功能 | 展示 `answer`，提示换说法 |
| `NEED_SLOT` | 选中的接口缺必填参数 | 按 `missing` 渲染输入框，把用户补充的内容再发一次 |
| `READY` | 写操作，参数齐了，等确认 | 渲染「确认执行」按钮，点了调 `/action/confirm` |
| `EXECUTED` | 执行成功 | 用 `execution.data` 渲染结果表格 |
| `FAILED` | 执行失败 / 会话过期 / 功能未启用 | 展示 `answer`（已脱敏） |

#### 响应 `data` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `phase` | string | 见上表 |
| `conversationId` | string | 后续多轮都带这个值 |
| `operation` | object\|null | 选中的接口，`UNSUPPORTED` 时为 null |
| `operation.id` | string | 接口唯一 id，形如 `op:breeding-service:GET:/pigs/{pigId}/quarantine-cert` |
| `operation.summary` / `method` / `path` | string | 中文摘要、HTTP 方法、服务内路径 |
| `operation.gatewayPath` | string | 拼好网关前缀的完整路径（执行用的是它） |
| `operation.module` / `service` | string | 所属模块名、服务名 |
| `slots` | object | 当前已收集的参数（键名与接口 schema 一致）。**执行完成后会被清空** |
| `missing` | array | 还缺的必填参数 |
| `missing[].name` / `.type` / `.hint` | string | 参数名、Java 类型、给用户的提示（如 `数字`） |
| `question` | string | 需要向用户说的话（追问或提示） |
| `answer` | string | 给用户看的最终答复。**模板生成，不含模型幻觉** |
| `execution` | object\|null | 执行结果，见下 |
| `execution.success` | boolean | 业务是否成功（兼顾 HTTP 与 `{"code":500}` 两种失败） |
| `execution.status` | int | 下游 HTTP 状态码，`-1` 表示请求没发出去 |
| `execution.elapsedMs` | long | 耗时 |
| `execution.data` | string | 下游原始响应（尽量格式化） |
| `execution.error` | string | 失败原因（已脱敏、截断 200 字） |
| `candidates` | array | 检索候选 `{id, summary, method, score}`，供排查「为什么选了这个」 |

#### 示例：缺参数（真实响应）

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "phase": "NEED_SLOT",
    "conversationId": "d1f38717-7bd7-4b2f-b1e0-65a704dc2422",
    "operation": {
      "id": "op:breeding-service:GET:/pigs/{pigId}/quarantine-cert",
      "summary": "查看产地检疫证明",
      "method": "GET",
      "path": "/pigs/{pigId}/quarantine-cert",
      "gatewayPath": "/api/v1/breeding/pigs/{pigId}/quarantine-cert",
      "module": "产地检疫证明管理",
      "service": "breeding-service"
    },
    "slots": {},
    "missing": [{ "name": "pigId", "type": "Long", "hint": "数字" }],
    "question": "要查看产地检疫证明，还需要补充：pigId（数字）。",
    "answer": "要查看产地检疫证明，还需要补充：pigId（数字）。",
    "execution": null,
    "candidates": [
      { "id": "op:breeding-service:GET:/pigs/{pigId}/quarantine-cert", "summary": "查看产地检疫证明", "method": "GET", "score": 0.944 },
      { "id": "op:breeding-service:GET:/records/certs", "summary": "产地检疫按批次分组（主行为一次出证，明细逐头）", "method": "GET", "score": 0.852 },
      { "id": "op:slaughter-service:GET:/slaughter/records/stamps", "summary": "检疫盖章按批次折叠", "method": "GET", "score": 0.571 }
    ]
  },
  "traceId": "3db5601d90d74a7bae6d71ad3f253d3d",
  "timestamp": 1795072712200
}
```

> 上面这段是**降级状态**（连不上千问）的真实返回，所以 `question` 前面带了提示句。
> 千问正常时这一句不会出现，追问话术由模型生成。

#### 示例：补上参数后执行成功（结构示例）

```json
{
  "phase": "EXECUTED",
  "conversationId": "d1f38717-7bd7-4b2f-b1e0-65a704dc2422",
  "operation": { "id": "op:breeding-service:GET:/pigs/{pigId}/quarantine-cert", "method": "GET", "...": "..." },
  "slots": {},
  "missing": [],
  "question": "已执行「查看产地检疫证明」。共 1 条。",
  "answer": "已执行「查看产地检疫证明」。共 1 条。",
  "execution": {
    "success": true,
    "status": 200,
    "elapsedMs": 87,
    "data": "{\n  \"code\": 200,\n  \"data\": { \"pigId\": 1, \"certNo\": \"...\" }\n}",
    "error": null
  },
  "candidates": []
}
```

> 注意两个细节：**执行成功后 `slots` 会被清空**（同一个接口连着跑两次多半不是用户想要的），
> 所以这里不是 `{"pigId":1}`；`candidates` 在 `/action/confirm` 路径下为空数组，
> 在 `/action/chat` 直接执行读操作时是本次检索的候选。
> `answer` 末尾那句是后端按响应结构补的条数结论（数组 → `共 N 条`，
> 分页结构 → `共 total 条，本页返回 M 条`），不是模型生成的话术。

#### 示例：写操作等确认（结构示例）

只有在 `ai.action.allowed-write-operations` 里点名放开了某个写接口才会出现：

```json
{
  "phase": "READY",
  "question": "即将执行「创建养殖场」（POST /farms），确认继续吗？",
  "slots": { "farmName": "示范猪场" },
  "missing": []
}
```

### 3.2 POST `/api/v1/ai/action/confirm`

用户点「确认执行」时调用。**参数不从前端回传** —— 前端把参数送回来，那条「参数白名单」
的路就被绕过去了。参数留在服务端会话里。

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `conversationId` | string | 是 | 上一步 `READY` 返回的 id |

```bash
curl -X POST 'http://localhost:8089/ai/action/confirm' \
  -H 'X-User-Id: 1' -H 'Authorization: Bearer <用户JWT>' \
  -H 'Content-Type: application/json' \
  -d '{"conversationId":"d1f38717-7bd7-4b2f-b1e0-65a704dc2422"}'
```

响应体与 `/action/chat` **完全一致**（同一个 `ActionChatResponse`），`phase` 通常是
`EXECUTED` 或 `FAILED`。

会话失效时（过期 / 已执行过 / 不是本人的）：

```json
{
  "code": 200,
  "data": {
    "phase": "FAILED",
    "conversationId": "not-exist",
    "question": "会话已过期，请重新描述一次要做什么。",
    "answer": "会话已过期，请重新描述一次要做什么。"
  }
}
```

会话 TTL 默认 10 分钟（`ai.action.session-ttl-minutes`）。

### 3.4 GET `/api/v1/ai/graph/search`

**调 Prompt 之前先看这个接口。** 如果这一步就没命中正确接口，改 Prompt 是白改。
它只检索、不执行，所以可以放心刷。

#### 请求参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `q` | string | 必填 | 自然语言，**不要做 URL 拼接，用 `encodeURIComponent` / `--data-urlencode`** |
| `topK` | int | 8 | 返回条数，服务端夹在 1~20 |

#### 响应

| 字段 | 说明 |

### 3.5 POST `/api/v1/ai/admin/graph/rebuild`

从各服务的 `/v3/api-docs` 重新拉一遍 schema，覆盖内存里的图谱。
**静态扫描拿不到泛型、默认值、body 嵌套结构，要精确参数就跑这个。**

- 需要 `X-User-Role` 是 `SUPERVISOR` 或 `ADMIN`
- 部分成功策略：某个服务连不上不影响其它服务，失败原因在 `services[].error` 里
- 建议在业务低峰跑，它会连续请求 8 个服务的文档接口

#### 请求参数

无请求体。

#### 响应

| 字段 | 说明 |
|---|---|
| `success` | 是否至少有一个服务成功 |
| `message` | 结论一句话 |
| `operationCount` / `moduleCount` | 重建后的规模 |
| `services[]` | `{service, ok, operationCount, error}` 逐服务结果 |

```bash
curl -X POST 'http://localhost:8089/ai/admin/graph/rebuild' \
  -H 'X-User-Id: 1' -H 'X-User-Role: ADMIN' -H 'Authorization: Bearer <用户JWT>'
```

```json
{
  "code": 200,
  "data": {
    "success": true,
    "message": "重建完成：8/8 个服务成功",
    "operationCount": 218,
    "moduleCount": 39,
    "services": [
      { "service": "breeding-service", "ok": true, "operationCount": 44, "error": null },
      { "service": "sales-service", "ok": false, "operationCount": 0, "error": "连接超时" }
    ]
  }
}
```

## 四、配置项

### 4.1 `ai.graph.*`（图谱与检索）

| 配置 | 默认 | 说明 |
|---|---|---|
| `ai.graph.enabled` | `true` | 总开关，关掉后 5 个接口都返回 503 |
| `ai.graph.seed-resource` | `arch-graph-seed.json` | classpath 下的种子文件名 |
| `ai.graph.refresh-on-startup` | `false` | 启动就去拉 8 个服务会拖慢启动，线上可打开 |
| `ai.graph.max-candidates` | `8` | 交给模型的候选数 |
| `ai.graph.min-score` | `0.15` | 低于此分直接丢弃，宁可说「没找到」也不硬凑 |
| `ai.graph.sources[]` | — | 8 个服务的 `docs-url` + `gateway-prefix` |
| `ai.graph.synonyms[]` | — | 口语 → 系统用词，加说法只改配置不用发版 |
| `ai.graph.stopwords[]` | — | 「帮我」「一下」这类不参与打分的词 |

**`gateway-prefix` 必须手写**：网关的 `StripPrefix` 每个服务不一样（breeding 是 3，
其余是 2），auth / trace 的服务内路径本身还带一级。这个前缀推导不出来，写错了就是 404。

**同义词必须用 `List` 不能用 `Map`**：Spring 的 `ConfigurationPropertyName` 只认小写字母
/数字/`-`，中文 key 会被**静默丢弃** —— 表现是「配置写了但完全没生效」，很难查。

```yaml
ai:
  graph:
    synonyms:
      - words: ["养殖场", "猪场", "养猪场"]
        expand: ["farm", "farms"]
      - words: ["检疫"]
        expand: ["quarantine", "cert"]
```

### 4.2 `ai.action.*`（执行策略）

| 配置 | 默认 | 说明 |
|---|---|---|
| `ai.action.enabled` | `true` | 执行总开关 |
| `ai.action.gateway-base-url` | `http://localhost:8080` | 走网关，复用 JWT 校验与令牌黑名单 |
| `ai.action.allowed-methods` | `[GET]` | 方法白名单 |
| `ai.action.allowed-write-operations` | `[]` | 要放开的写操作，逐个填 operationId |
| `ai.action.denied-services` | `[auth-service]` | 认证服务一律不执行 |
| `ai.action.denied-path-prefixes` | `[/system, /internal, /ingest, /ai/]` | 按**路径段**匹配 |
| `ai.action.timeout-seconds` | `30` | 下游超时 |
| `ai.action.max-result-chars` | `4000` | 返回给前端的 `execution.data` 上限 |
| `ai.action.session-ttl-minutes` | `10` | 多轮会话过期时间 |
| `ai.action.session-max` | `5000` | 会话数上限，满了淘汰最久未活跃的 |
| `ai.action.rate-limit-per-minute` | `20` | 每用户每分钟执行次数 |

**要放开一个写操作**，先从 `/ai/graph/search` 查到它的 `id`，然后：

```yaml
ai:
  action:
    allowed-write-operations:
      - op:breeding-service:POST:/farms
```

放开后该接口在对话里会走 `READY` → 用户点确认 → 才真正执行。


## 七、已知限制

1. **不做跨接口编排**。「查出 A 再拿结果去做 B」要两次对话。真正的 function calling
   循环是下一步。
2. **日期换算是模型算的**。「上个月」由千问按注入的今天换算，跨年边界建议复核。
3. **写操作被过滤后可能落到语义较远的只读接口**。候选在交给模型前已过滤掉不可执行的，
   于是「今天卖了多少猪肉」这种，写接口看不见、只读接口又被挑中。
   降级时会在回答前明确提示；要根治得让「因写操作被拒」这件事显式回到模型面前。
4. **静态扫描拿不到泛型参数**，`@RequestParam List<Long> ids` 扫出来是 `List<Long>`，
   要精确 schema 跑一次 rebuild。
5. **`auth-service` 整个被拉黑**，哪怕只是「查一下有多少用户」也不执行。
6. **会话存在内存里**，重启即丢，多实例部署需要换成 Redis。
7. **不支持 SSE**。这个场景的输出是结构化结果不是流式文本，所以故意用普通 JSON。
