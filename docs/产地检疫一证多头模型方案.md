# 产地检疫「一证多头」模型方案

> 背景：产地检疫出证已接入扫码登记终端（通道 `QUARANTINE`，设备 `QSCAN-001`）。
> 当前实现按「一证一头猪」落地，覆盖单头出证与全部演示场景。
> 本文说明当检疫证按**批次**签发时（一张证写「生猪 120 头」），数据模型要怎么改。

## 一、问题是什么

现实中的《动物检疫合格证明》多数**按批次签发**：一张证对应一个货主、一个启运地、一个目的地，
「数量」栏写的是头数（如 120 头），并不逐一列出耳标。而系统现有模型是单头对单证：

```sql
CREATE TABLE quarantine_certificate (
  pig_id BIGINT NOT NULL,        -- 单头
  cert_no VARCHAR(32) NOT NULL,
  ...
  UNIQUE KEY uk_cert_no (cert_no),
  INDEX idx_pig (pig_id)
);
```

服务层还有一条业务约束：**一头猪同一时间只能有一张有效证**（换发须先作废原证）。
这两条在单头出证下没问题，遇到批次证就都撞墙：

| 冲突点 | 具体表现 |
|---|---|
| `pig_id` 单值 | 一张证挂 120 头猪，没有位置放 |
| `uk_cert_no` + Service 唯一性检查 | 按「一证 N 行」存会直接撞唯一键 |
| 入场查验的核验口径 | 核验公式是「证存在 + 未过期 + **证上耳标与闸口扫描的耳标一致**」，批次证上没有单头耳标，第三个条件无从比对 |
| 追溯查询 | 按猪查证（`GET /breeding/pigs/{id}/quarantine-cert`）在批次证下要能反查到「这张批次证覆盖了它」 |

## 二、三种可选模型

### 方案 A：证—猪 关联表（推荐）

```sql
CREATE TABLE quarantine_cert_pig (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  cert_id BIGINT NOT NULL,
  pig_id BIGINT NOT NULL,
  ear_tag_no VARCHAR(32),
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_cert_pig (cert_id, pig_id),
  INDEX idx_pig (pig_id)
);
```

`quarantine_certificate.pig_id` 保留但改为可空，语义降级为「主管联猪」（单头证时仍填，便于兼容旧读路径）。

- **优点**：一证多头、一猪多证两个方向都能查；证号唯一性不受影响；核验仍可按耳标走关联表；存量数据可平移。
- **缺点**：多一张表、多一次 join；「一头猪一张有效证」的约束从表级移到查询级（本来也已经在 Service 层）。

### 方案 B：给证加「头数 / 批次号」，一证只落一条

`quarantine_certificate` 增加 `batch_no`、`head_count`，`pig_id` 允许 NULL（批次证不指向具体猪）。

- **优点**：改动最小，最贴近证面本身；批次证就是一条记录，没有冗余。
- **缺点**：单头猪的追溯链上「它有没有有效证」要靠批次号反查，一猪一档被弱化；入场查验按耳标核验时，
  需要额外一步「先用耳标找到所属批次，再核该批次的证」，链路更长。

### 方案 C：一证拆多条（同证号 N 行）

- 与 `uk_cert_no` 直接冲突，必须去掉证号唯一键 → 同时失去「同一张证不得重复登记」这道最有效的防伪闸门。
- **不推荐**，仅列出以说明为何不这么做。

## 三、推荐：方案 A

选它的核心理由是**它同时满足两个方向的查询**，而 B/C 都只能满足一个：

- 监管视角「这张证覆盖了哪些猪」→ `cert_id → pig_id`
- 追溯视角「这头猪凭哪张证调运的」→ `pig_id → cert_id`
- 防伪视角「证号是否重复登记」→ 仍由 `uk_cert_no` 保证，不受影响

### 落地路径（建议分两步，第一步不改任何行为）

**第一步：只加表与数据，不动逻辑**

1. 建 `quarantine_cert_pig`
2. 存量迁移：现有 18 张证各按 `pig_id` 生成一条关联记录
3. `pig_id` 改为可空（历史读路径继续可用）

**第二步：切核验与展示**

4. 核验接口 `GET /breeding/internal/quarantine-certs/verify` 改两级查找：
   先按 `earTagNo` 在关联表里找有效证 → 找不到再按 `certNo` 直查 → 都无则 `valid=false`
5. 扫码登记通道（`QuarantineChannelHandler`）支持多头报文：
   报文给 `earTagNos: ["...", "..."]` 或只给 `headCount`（后者不逐头落关联）
6. 前端产地检疫页由「一行一头猪」改为「一行一张证」（证下可展开看覆盖的猪），
   追溯侧仍保留「按猪查证」的入口

### 明确不做的事

- 不去掉 `uk_cert_no`——证号唯一是这套体系里最有效的防重复/防伪造闸门。
- 不让批次证绕过「官方兽医实名」与「登记留痕上链」——批次只是颗粒度不同，责任口径不变。

## 四、当前实现的范围与限制（2026-10-08）

已实现并验证：

- 扫码登记终端（`QSCAN-001`）走接入层 `QUARANTINE` 通道，自动登记并上链
- 校验：耳标必须在档、证号全局唯一、官方兽医取自证面且必填、扫描件报了就必须真实存在
- 幂等：同一张证重复登记返回既有记录；一头猪已有有效证则转「待人工确认」（换发须先作废原证）
- 来源标记：`quarantine_certificate.source = DEVICE`、`source_ref = QSCAN-001`，人工出证记 `MANUAL`

**未实现（本文待办）**：批次证。当前一张证只能登记一头猪，报文的耳标字段是单值。
在真实批次出证场景上线前，需要先走完上面「第二步」。

## 五、一个顺带的提醒：扫码防不了假证

扫码登记终端解决的是**录入准确性**（替代手抄证面信息），不解决**证的真伪**：
一张真单子扫十次，只要证号不同就能登记十次（同一证号会被幂等挡住）。

要真正防住伪造与重复使用，还必须接**官方检疫平台的核销回查**（查询「此证是否已使用/已核销」）。
在那之前，系统能保证的只是「证号在本系统内不重复、耳标有档、签发人落实名」。
