# 来源管控与上链可信方案

> 一句话：区块链只能保证「上链之后改不了」，管不了「上链之前是谁写的」。
> 所以关键环节的数据写入权必须收归设备；人工不是被消灭，而是被降级为**有申请、有理由、有留痕的兜底入口**。

---

## 0. 四句话讲完最终形态

| # | 规则 | 落点 |
| --- | --- | --- |
| 1 | **采集入口**：数据采集类环节的人工新增端点**整条删除**，只认设备通道；唯一保留的人工采集口是「产地检疫出证」（法定签发、暂无设备通道），须先申请限时兜底解锁 | 人工 `@PostMapping` 已移除 + `TraceStage` 策略 + 兜底解锁票据 |
| 2 | **编辑**：结论类字段禁止原地改，只能「作废 + 重录」；非结论字段可改，但改动单独上链 | `SourceGuard.rejectConclusionChange()` |
| 3 | **作废/更正与新增同级受控**，堵死「用作废绕开管控」 | 作废四列 + 作废事件上链 + `SourceGuard.requireVoidAllowed()` |
| 4 | **追溯统一取"当前有效记录"**，作废记录不物理删、带标注保留 | `@TableLogic(void_flag)` + 追溯侧 `voided` 标注 |

## 1. 为什么不能靠"删掉所有人工录入"来防篡改

| 做法 | 实际效果 |
| --- | --- |
| 一刀切删掉**所有**人工入口（含签收、出证、复核） | 上链前的数据依然可造假：设备密钥泄露、假设备登记、模拟器脚本本身就是现成的伪造工具。防的是"填表单的人"，不是"造假本身"；而且一刀切会把现场断网、设备故障这类真实情况变成业务停摆 |
| **只删采集类**环节的人工新增入口（本方案采用） | 8 个有设备通道的采集环节只认设备写入，人工再也无法凭空造一条采集数据；人工能力全部收敛到「对设备已报上来的数据做实名复核」 |
| 关键环节设备独占 + 异常数据实名复核 + 兜底解锁申请制 | 造假的成本从「填个表单」抬到「偷密钥 + 绕过服务端校验 + 冒用账号 + 留下申请记录」 |
| 全链路留痕 + 来源标记 + 作废留痕 | 审计口径成立：任何一条数据都能回答"谁写的、什么时候写的、是设备写的还是人写的、后来有没有被作废、为什么" |

结论：**不是消灭人工，而是让剩下的人工介入变得可识别、可追责。**
采集类入口删到只剩一个（产地检疫出证），而且那一个也必须实名 + 申请解锁。

## 2. 策略模型

三个策略，定义在 `common-core` 的 `SourcePolicy`：

| 策略 | 含义 | 人工新增入口 |
| --- | --- | --- |
| `DEVICE_ONLY` | 设备独占 | **关闭**，服务端直接拒绝（错误码 2003），连兜底票据也不接受 |
| `DEVICE_PREFERRED` | 设备优先 | **默认隐藏**，须先申请兜底解锁票据（`X-Fallback-Ticket`），且强制标注 `source=MANUAL` + 操作人 + 上链 |
| `MANUAL_ALLOWED` | 人工可录 | 正常可用 |

环节与策略的**唯一真相源**是 `common-core` 的 `TraceStage`（代码内置，不放数据库，避免多服务之间不一致）：

| 环节 | 目标表 | 设备通道 | 策略 | 人工新增入口 | 为什么 |
| --- | --- | --- | --- | --- | --- |
| 养殖建档（耳标） | `pig_individual` | TAG | **设备独占** | 已删除 | 耳标读写器佩戴即建档；人工建档等于凭空造一头猪 |
| 免疫注射 | `vaccine_record` | VACCINE | **设备独占** | 已删除 | 智能注射器自动记录批号剂量，批号是事后追责的关键 |
| 产地检疫出证 | `quarantine_certificate` | 无 | **设备优先** | **保留**（须兜底解锁） | 唯一的例外：检疫证由官方兽医法定签发，暂无设备通道。删掉人工则检疫证永远出不了，入场查验核验证件整条链断掉 |
| 入场查验 | `entry_inspection` | ENTRY | **设备独占** | 已删除 | 查验结论直接决定生猪能否入厂 |
| 瘦肉精检测 | `ractopamine_test` | RACTOPAMINE | **设备独占** | 已删除 | 涉及食品安全红线，仪器读数不得代填（宰前抽检，排在屠宰检验之前） |
| 屠宰检验 | `slaughter_inspection` | INSPECTION | **设备独占** | 已删除 | 合格/不合格决定肉品去向，最不能人工补录的一环（含宰前 + 宰后） |
| 胴体盖章 | `carcass_stamp` | STAMP | **设备独占** | 已删除 | 盖章是法定授权行为，机器执行、系统留痕 |
| 分割批次创建 | `split_batch` | SPLIT | **设备独占** | 已删除 | 扫码称重台自动建批次，人工建批次会让重量无据可查 |
| 冷链温度 | `temperature_log` | TEMPERATURE | **设备独占** | 已删除 | 温度由传感器自动采集，人工补测等于给自己写合格证 |
| 门店签收 | `store_receipt` | RECEIPT | 人工可录 | 保留 | 签收是责任转移点，天然以人为主 |
| 零售售出 | `retail_sale` | SALE | 人工可录 | 保留 | 收银天然以人为主 |

**顺序即业务链**：上表**按业务发生顺序**排列，与 `TraceStage` 的枚举声明顺序严格一致——`SourcePolicyRegistry.list()` 直接按枚举 `values()` 输出，因此这份顺序同时决定了前端「来源策略」表格与「兜底解锁」环节下拉的展示次序。调整顺序时请同步核对侧边栏菜单（`menuConfig.ts`）、追溯页时间轴（`TraceSearch.vue`）与设备通道标签（`api/modules/ingest.ts` 的 `CHANNEL_LABELS`）。

> 两点设计说明：
> 1. **「产地检疫出证」是刻意保留的例外**，也是全项目唯一没有设备通道的采集环节。
>    检疫证是入场查验的前置凭证——把它一起关掉，整条追溯链从源头就断了。
>    所以策略留成「设备优先」：不能一刀切关闭，但必须实名 + 申请兜底解锁。
>    **界面入口**：`养殖管理 → 产地检疫`（`views/farm/QuarantineCertList.vue`，可直接看「哪些猪已出证 / 未出证 / 证已过期」并出证、作废）；
>    也可从 `养殖管理 → 生猪档案 → 该行「产地检疫」` 进入同一弹窗（`views/farm/QuarantineCertDialog.vue`）。
>    注意业务顺序是 **养殖建档 → 免疫注射 → 产地检疫出证 → 入场查验**：一头猪要先有档、
>    再有证，才能被闸口核验放行；建完档不出证，这条链在界面上就是断的。
>    另需注意：出证接口 `POST /breeding/pigs/{pigId}/quarantine-cert` 的
>    `QuarantineCertDTO.pigId` 为 `@NotNull`，**请求体必须带 `pigId`**（路径里的同名参数由控制器覆盖）——
>    前端 `pigApi.uploadQuarantineCert()` 已自动合并，漏了会在参数校验阶段就报「生猪ID不能为空」，
>    根本走不到来源管控。
> 2. **`SourcePolicyRegistry.resolve()` 有兜底退化**：若某环节被配置成 `DEVICE_ONLY`
>    却又没有设备通道，会自动退化为 `MANUAL_ALLOWED`，避免"配置一改就把业务锁死"。
>    注意该退化**只针对 `DEVICE_ONLY`**：`QUARANTINE` 配的是 `DEVICE_PREFERRED`、通道为 `null`，
>    因此解析结果仍是 `DEVICE_PREFERRED`——出证与作废**都要**兜底票据。

## 3. 兜底解锁：把"人工口子"变成"可追溯的口子"

设备优先环节的人工入口默认是关着的。"关"不等于"业务上永远不会需要"——耳标读写器坏了、
现场没网、历史数据要补录，这些都是真事。所以留一条路，但这条路必须**先申请**：

```
申请人 ──① POST /ingest/fallback/unlock（环节 + 理由≥4字）──> ingest-service
                                                              │ 记录 source_fallback_unlock
                                                              │ 签发 HMAC-SHA256 限时票据
                                                              ↓
        ② 前端存入 sessionStorage，请求拦截器自动附加 X-Fallback-Ticket
                                                              ↓
   人工录入请求 ──③ 业务服务 SourceGuard 本地验签 → 放行并标注 source=MANUAL + 上链
```

票据格式：`v1|环节|失效时间戳|申请人ID|申请人姓名|签名`，最长 24 小时，默认 120 分钟。

**为什么是签名票据而不是"回调 ingest 查一下解锁状态"**：
兜底场景本身就发生在设备/网络异常时，再让业务服务同步依赖注册中心和另一个服务，
等于把补救路径交给运气。签名票据可以本地验证，链路短、失败面小。

**为什么申请记录也要落库**：票据本身只能证明"允许录入"，证明不了"为什么允许"。
`source_fallback_unlock` 表把理由、申请人、申请时间、失效时间、提前关闭原因全部留档，
所以每一次兜底录入都能回溯到一次具体的申请。

**提前关闭**：`POST /ingest/fallback/unlock/{id}/close`（带关闭原因）。
设备恢复了就把口子关掉，不用等票据自然过期——口子开着的时间越短越好。

## 4. 四道防线

```
采集请求 ──①端点上不存在（405）──> 业务服务 ──②SourceGuard 校验（唯一人工口 / 作废）──> 数据库
                                      ↑
      管理端页面 ──③不展示录入入口─────┘
                                      ↑
      接入层「待人工处理」队列 ──④实名复核放行（有原始报文 + 理由）
```

**① 端点不存在**（最强，也是本次改动的核心）
8 个采集环节的人工新增 `@PostMapping` 已从控制器**整条删除**，只留下 `@GetMapping`（列表/详情）。
因此对同一路径发 POST 只会撞上 `405 Method Not Allowed`——请求在**方法匹配阶段**就被排除，
连业务代码都不会进入。这比"进到业务代码再抛异常"更干净：没有可以漏判的分支，
也没有可以被绕过的重载方法。

被删除的端点是：

| 服务 | 端点 | 对应环节 |
| --- | --- | --- |
| slaughter | `POST /slaughter/entries` | 入场查验 |
| slaughter | `POST /slaughter/ractopamine` | 瘦肉精检测 |
| slaughter | `POST /slaughter/inspections` | 屠宰检验 |
| slaughter | `POST /slaughter/stamps` | 胴体盖章 |
| breeding | `POST /breeding/pigs` | 养殖建档 |
| breeding | `POST /breeding/pigs/{id}/vaccines` | 免疫注射 |
| distribution | `POST /distribution/splits` | 分割批次 |
| distribution | `POST /distribution/transports/{id}/temperature` | 冷链温度 |

> 设备通道走的是完全独立的一组内部端点（`*/internal/ingest/*`，只由接入层调用、不经网关），
> 与人工入口在代码上没有共用路径，因此删除人工端点不影响设备链路。

**② SourceGuard 守剩下的两处**（唯一人工口 + 作废）
人工新增入口只剩产地检疫出证一处，它仍走统一闸门：

```java
ManualOperator operator = sourceGuard.requireManualAllowed(TraceStage.QUARANTINE);
// 设备优先 → 校验 X-Fallback-Ticket 签名与时效，通过后返回操作人身份
// 设备独占 → 抛 BusinessException(FORBIDDEN)，票据也无效
```

缺票据时的提示：

```json
{ "code": 2003, "message": "【兜底管控】产地检疫出证的人工新增需要有效的兜底解锁凭证：未提供有效的兜底解锁凭证。请到「设备接入 → 兜底解锁」说明原因并申请一张限时通行证后重试。" }
```

作废（`requireVoidAllowed`）走同一套规则，见第 5.2 节。

**③ 前端不展示**（表现层，最弱）
`SourceGuardBar.vue` 按 `/ingest/source-policy` 返回的策略决定渲染什么：
- 设备独占 → 提示条 + 跳转「设备接入」链接，无录入按钮；
- 设备优先 → 「设备优先环节」标签 + 「申请兜底解锁」按钮 + 实际的录入槽位。

前端只负责不让正常用户走错路，**不承担安全职责**——端点已经删了，改前端也绕不过去。

**④ 接入层复核留痕**（补救路径）
设备报了但条件不满足（如耳标没有档案、胴体批次不存在），数据进 `ingest_staging` 的
「待人工处理」队列。关键环节的 `approve` 强制要求：

- 处理人必须是登录账号（`X-User-Id`），不允许 `unknown`；
- 必须填写放行理由（`remark`），与原始报文一起留档。

也就是说：**人工能做的只有"对设备已报上来的数据做复核"，不能"凭空造一条数据"。**

## 5. 编辑与作废：把"偷偷改"变成"只能公开推翻"

### 5.1 字段分两类

| 类别 | 举例 | 处理方式 |
| --- | --- | --- |
| **结论类**（决定这条记录是什么） | 检验结论 `result`、盖章号 `stampNo`、耳标号 `earTagNo`、检测结果、兽医签名、胴体编号 | **禁止原地修改**，只允许「作废 + 重录」 |
| **说明类**（补充与流转） | 备注 `remark`、附件 `fileIds`、圈舍 `penNo`、批次备注 `note`、检测报告 URL | 允许修改，但改动单独上链 |

实现：各 `update` 方法用 `SourceGuard.sameValue()` 逐字段比对，把变了且属结论类的字段名收进列表，
交给 `sourceGuard.rejectConclusionChange(stage, changedFields)` 统一拒绝：

```json
{ "code": 2003, "message": "【来源管控】屠宰检验的结论字段（检验结论、兽医签名）不允许原地修改。正确做法是作废原记录并重新录入，作废动作会实名上链留痕。" }
```

> `sameValue()` 按数值语义比较（`BigDecimal.compareTo`），避免前端传 `1`、库里存 `1.0`
> 被误判成"结论被改了"，把正常提交挡在门外。

### 5.2 作废与新增同级受控

删除入口全部改为**作废**（`POST .../{id}/void`，请求体 `{ "reason": "..." }`），
作废走 `SourceGuard.requireVoidAllowed(stage, reason)`，与新增**同级受控**：

| 策略 | 作废要求 | 为什么 |
| --- | --- | --- |
| `DEVICE_ONLY`（设备独占） | 实名 + 理由≥2 字；**不要求票据** | 该环节人工新增入口本就关闭，无从"绕开"；但作废会打 `void_on_device_only` WARN 日志供审计侧主动发现——设备录错的数据必须能清掉，否则只会在库里越积越脏 |
| `DEVICE_PREFERRED`（设备优先） | 实名 + 理由 + **有效兜底票据** | 该环节的人工写入本来就要申请解锁，作废属同类人工动作；否则「新增进不来、那就把设备写的废掉」会成为新的绕行路径 |

**这样"用作废绕开管控"和"用作废删掉不利数据"都行不通**——
作废会在链上留下一条带实名与理由的记录，删数据反而比自己写更显眼。

作废的统一列（`backend/init-sql/16-void-and-fallback.sql` 幂等添加）：

| 列 | 说明 |
| --- | --- |
| `void_flag` | 0=有效 1=已作废；**同时是 MyBatis-Plus 的 `@TableLogic` 标记** |
| `void_reason` | 作废理由，必填 |
| `void_operator` | 作废操作人（实名） |
| `void_time` | 作废时间 |

覆盖 12 张表：`entry_inspection` / `slaughter_inspection` / `ractopamine_test` / `carcass_stamp`
/ `pig_individual` / `vaccine_record` / `quarantine_certificate` / `split_batch`
/ `temperature_log` / `store_receipt` / `retail_sale`（以上 11 张见 `16-void-and-fallback.sql`）
/ `carcass_batch`（`17-reconcile-chains.sql` 补上——16 号漏了这张，导致"批次删不掉也作废不了"，
而它恰恰是下游分割批次与零售商品的引用对象）。

> 尚未覆盖：`cold_chain_transport`（运单）仍无作废列，靠 `status` 生命周期表达状态；
> 若将来要作废运单，需照同一口径补列。

> 为什么 `void_flag` 一个列干两件事：作废的业务语义和"查询时不再返回"的技术语义在这里完全重合。
> 分成两列（`void_flag` + `deleted`）只会制造"业务已作废但查询还能查到"的一类脏 bug。
> 历史遗留的 `deleted`、`slaughter_inspection.status=3`、`carcass_stamp.status=2` 在 16 号
> 脚本里已统一迁移到 `void_flag`。

**为什么用自定义 `@Update` 而不是 `removeById`**：逻辑删除只会把标记翻成 1，
写不下"为什么作废、谁作的废"，而这两项恰恰是事后最需要回答的。

### 5.2.1 作废必须沿链向下传导

只把源头那一行翻成"已作废"是不够的——下游还挂着"有效"的记录，等于**已作废的猪，肉还在货架上**。
`backend/init-sql/17-reconcile-chains.sql` 把这条规则落成可重复执行的修复：

> 胴体批次的关联生猪**全部**已作废 → 批次作废；批次作废 → 其派生分割批次作废；
> 分割批次作废 → 关联零售商品作废。逐层写清理由、操作人（`system-reconcile`）与作废事件上链。

⚠ **实现上的坑**：`split_batch.parent_batch_id` 是**按层级指向不同表**的——
`split_level = 1` 时指向 `carcass_batch.id`，`split_level >= 2` 时指向 `split_batch.id`，
而两张表的 id 空间是重叠的（同时存在 `carcass_batch 18` 与 `split_batch 18`）。
不按 `split_level` 分流就会把"属于有效猪的批次"误判成"上一层的子级"而连坐作废（实测踩到过）。

另一个坑：MySQL 在 `INSERT…SELECT` 里对**关联外层的 `JSON_TABLE`** 判定会静默给空集，
换成 `JSON_CONTAINS(cb.pig_ids, CAST(p.id AS JSON))` 才可靠。

### 5.2.2 作废之后必须能重录

`quarantine_certificate` 原先在 `pig_id` 上压着 `UNIQUE KEY uk_pig`，即"一头猪一辈子只能有一行证书"。
作废只是把 `void_flag` 翻成 1、行还留在表里，于是重出证会被唯一键顶掉，抛 `DuplicateKeyException`
（前端看到"系统内部异常"）——**这一环的核心闭环（出证 → 作废 → 重出证）本身就是断的**。

`18-quarantine-cert-reissue.sql` 去掉该唯一约束、改普通索引；
"同一头猪同时只能有一张有效证书"由 `QuarantineCertServiceImpl.uploadCert` 查有效记录来保证。
`cert_no` 的唯一约束保留：编号不可复用，重录要换新编号。

### 5.3 追溯侧怎么体现

- **取数**：所有常规查询与追溯取数都只返回 `void_flag = 0` 的记录（`@TableLogic` 自动加条件）；
- **标注**：作废记录不物理删除，追溯链额外返回 `voidedRecords` + `voidedSummary`，
  页面用一条警示条列出「哪一环节、哪条单据、为什么被作废、谁作的废、什么时候」，
  并明确告知「页面展示的是作废后当前有效的记录」。

```json
{
  "voidedRecords": [
    { "stage": "INSPECTION", "stageLabel": "屠宰检验", "bizNo": "SI20260922001",
      "reason": "结论录入有误，已作废重录", "operator": "admin", "time": "2026-10-03 15:20" }
  ],
  "voidedSummary": "该批次有 1 条记录已被作废重录（涉及：屠宰检验）。页面展示的是作废后当前有效的记录；作废理由与实名操作人已留档，可展开核对。"
}
```

作废查询用原生 `@Select` 显式绕过逻辑删除（只读，不参与任何写路径）：
`SlaughterInternalController` / `BreedingInternalController` 的 `voided` 汇总即是此用途。

> 这条设计的用意：「记录凭空消失」和「记录被公开作废」在追溯可信度上完全是两回事。
> 前者让人怀疑系统藏了东西，后者让人相信系统没藏东西。

## 6. 链上存证的增强

1. **人工写入也必须带来源**
   唯一保留的人工采集口（产地检疫出证）写入 `source=MANUAL` + `source_ref=操作人`，
   链上索引时可以直接按来源过滤——凡标 `DEVICE` 的都来自设备通道，两者不会混。

2. **每一个"人为动作"都单独上链**

   | 事件类型 | bizKey | 内容 |
   | --- | --- | --- |
   | `ENTRY_INSPECTION` / `RACTOPAMINE_TEST` / `SLAUGHTER_INSPECT` / `CARCASS_STAMP` | 业务键 | 正常写入 |
   | `*_MANUAL_EDIT` | `<业务键>:MANUAL_EDIT:<时间戳>` | 说明性字段被人工修改：操作人、改动字段、原来源 |
   | `*_VOID` | `<业务键>:VOID` | 作废动作：操作人、作废理由、原来源 |
   | `PIG_INDIVIDUAL` / `VACCINE_RECORD` / `SPLIT_BATCH` | 业务键 | 设备通道写入（采集类人工新增入口已删除，`fallback` 标记已不再产生） |

   结果是：**"这条检验结论被改过 / 被作废过，改的人是谁、为什么"——链上查得到，删不掉。**

3. **字段防篡改**
   人工入口一律从 DTO 中排除 `source` / `sourceRef` / `rawPayload` 三个字段
   （`BeanUtils.copyProperties(..., "source", "sourceRef", "rawPayload")`），
   调用方无法把自己伪装成设备采集；`X-Fallback-Ticket` 由服务端 HMAC 签名，客户端伪造不了。

### 操作人身份是怎么落到记录上的

| 载体 | 内容 | 说明 |
| --- | --- | --- |
| `X-User-Id` | 用户ID（对应 `sys_user.id`） | 系统既有约定，下游有按 `Long` 解析的地方（如举报接口），**不能改** |
| `X-User-Name` | 登录用户名 | 透传头，来源令牌里的 `userName` 声明；老令牌没有该声明时退回用户ID |
| 业务表 `source_ref` | 登录用户名 | 人看得懂，例如 `admin` |
| 业务表 `void_operator` | 登录用户名 | 作废动作实名留档 |
| `ingest_staging.handler` | `用户名(用户ID)` | 两个都留：用户名给人看，ID 给机器对账 |
| `source_fallback_unlock.applicant_name` / `applicant_id` | 用户名 + 用户ID | 兜底申请实名留档 |
| 上链 payload `operator` / `applicant` | 登录用户名 | 链上存证与业务表口径一致 |

> 为什么要动令牌：原来的 access token 里只有用户ID（subject 即 ID），
> 于是"谁改的"只能记成一串数字，审计时还得回头查用户表。
> 现在登录令牌额外带 `userName` 声明，网关解析后透传 `X-User-Name`，
> 关键环节的人工介入就能直接以人名留痕——**留痕要留得看得懂才算留痕**。

## 7. 应急开关

默认不配置就是最严形态。仅在演练/故障需要临时放开时，在对应服务的 `application.yml` 里加：

```yaml
pork:
  trace:
    source:
      enforce-device-only: false          # 总开关：所有 DEVICE_ONLY 降为 DEVICE_PREFERRED（仍标来源）
      overrides:                          # 单环节覆盖，平时留空
        SLAUGHTER_INSPECTION: MANUAL_ALLOWED
      fallback-secret: ${PORK_FALLBACK_SECRET:}   # 兜底票据签名密钥，生产必须外部注入
      fallback-ttl-minutes: 120                    # 兜底票据有效期，最长 24 小时
```

- 配置写错（不认识的环节名/策略名）**不会阻断启动**，按默认严格策略走；
- 覆盖生效时启动日志会打 `source_policy_override_active` 警告，避免"放开过就忘了收回来"；
- 未配置 `fallback-secret` 时启动会打告警——用默认密钥签发的票据，等于没有票据。

## 10. 与设备自动录入的关系

| | 自动录入（原有） | 来源管控 + 作废留痕（本次） |
| --- | --- | --- |
| 解决的问题 | 数据**怎么进来** | 数据**允不允许这样进来**、**改过之后说不说得清** |
| 关键机制 | 通道 + 设备密钥 + staging + 幂等 | 策略 + 服务端拦截 + 兜底票据 + 结论字段保护 + 作废留痕 + 链上来源 |
| 覆盖面 | 10 条通道 / 15 台设备 | 11 个溯源环节（8 个设备独占且人工入口已删除、1 个保留但须兜底解锁、2 个人工可录）；12 张表统一作废语义 |

两者叠加后的完整口径是：

> **采集类环节只能由设备写入；唯一例外（产地检疫出证）必须实名 + 先申请解锁，全程留痕并上链；
> 结论写错了不许改，只能公开作废、重新采集；作废本身也受同一套管控、也上链；
> 追溯一律只展示当前有效记录，同时把"哪条被作废了、为什么"如实标出来。**

最后一句尤其重要：**这套机制不承诺"数据一定是真的"，它承诺的是"数据是假的，你查得出来"。**
链上、留痕、作废标注，做的都是同一件事——把不可发现变成可发现。
