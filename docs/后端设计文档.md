### 2.2 各服务职责

| 服务名称 | 端口 | 职责范围 | 核心业务表 |
|---------|------|---------|-----------|
| `gateway-service` | 8080 | API网关：JWT鉴权校验、IP黑名单、接口限流（令牌桶）、请求日志、跨域处理、路由转发 | — |
| `auth-service` | 8081 | 认证授权：登录/登出/Token刷新、RBAC角色权限、CA证书管理、操作日志 | `sys_user`, `sys_role`, `sys_permission` |
| `breeding-service` | 8082 | 养殖免疫：生猪档案、耳标绑定、疫苗注射、出栏申报审批、产地检疫证明上传 | `pig_individual`, `vaccine_record`, `slaughter_apply`, `quarantine_certificate` |
| `slaughter-service` | 8083 | 屠宰检疫：入场查验、宰前/宰后检验、瘦肉精检测、检疫合格盖章 | `entry_inspection`, `slaughter_inspection`, `ractopamine_test`, `carcass_stamp` |
| `distribution-service` | 8084 | 分割配送：胴体批次、白条猪→分割肉拆分、冷链运输、温度打卡、门店签收 | `carcass_batch`, `split_batch`, `cold_chain_transport`, `temperature_log`, `store_receipt` |
| `sales-service` | 8085 | 市场销售：二维码生成/激活、销售登记、过期预警、产品召回 | `retail_sale`, `expire_warning`, `recall_order` |
| `trace-service` | 8086 | 应急追溯：批次上下游反查、一键验真、举报管理 | `complaint_report` (关联查询所有业务表) |
| `blockchain-service` | 8087 | 区块链适配：智能合约调用、交易管理、上链重试、链上查询、哈希验真 | `blockchain_record` |
| `file-service` | 8088 | 文件管理：上传/下载/预览、SHA-256计算、类型校验、缩略图生成 | 文件系统 + `file_metadata` |

### 2.3 服务间调用关系

```
breeding ──→ file  (上传检疫证)
breeding ──→ blockchain  (检疫证上链) [异步MQ]

slaughter ──→ file  (上传检验照片)
slaughter ──→ blockchain  (双检报告上链) [异步MQ]

distribution ──→ file  (上传分割车间照片、签收照片)
distribution ──→ blockchain  (批次拆分上链、签收上链) [异步MQ]

sales ──→ distribution  (查批次信息)
sales ──→ blockchain  (销售激活上链、召回令上链) [异步MQ]

trace ──→ breeding, slaughter, distribution, sales  (跨服务查询溯源链路)
trace ──→ blockchain  (验真)
trace ──→ file  (举报照片上传)
```

**同步调用**：仅查询和文件上传为同步调用（Feign / RestTemplate）
**异步调用**：所有上链操作通过 RabbitMQ 消息投递，不阻塞用户操作

## 三、数据库设计

### 3.1 数据库命名规范

| 类别 | 规范 | 示例 |
|------|------|------|
| 数据库名 | 小写+下划线，按服务分库 | `db_breeding`, `db_slaughter` |
| 表名 | 小写+下划线，snake_case | `pig_individual` |
| 字段名 | 小写+下划线 | `ear_tag_no`, `create_time` |
| 主键 | `id` BIGINT AUTO_INCREMENT | — |
| 索引名 | `idx_表名缩写_字段名` | `idx_pig_farm` |
| 唯一索引 | `uk_表名缩写_字段名` | `uk_pig_ear_tag` |
| JSON字段 | 内容为`["a","b"]`或`{"k":"v"}` 无深层嵌套 | `file_ids`, `organ_check` |
| 必备字段 | `id`, `create_time` 所有表必含；`update_time` 需要追踪变更的表必含 | — |

### 3.3 核心表结构

#### 3.3.1 养殖免疫库 (db_breeding)

```sql
-- ==================== 生猪个体表 ====================
CREATE TABLE pig_individual (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    ear_tag_no      VARCHAR(32)  NOT NULL UNIQUE COMMENT '耳标号（RFID电子耳标编码）',
    farm_id         BIGINT       NOT NULL COMMENT '养殖场ID',
    breed           VARCHAR(32)  COMMENT '品种：长白猪/大白猪/杜洛克/二元杂/三元杂',
    birth_date      DATE         COMMENT '出生日期',
    pen_no          VARCHAR(16)  COMMENT '圈舍编号',
    source          VARCHAR(64)  COMMENT '来源：自繁/外购-供应商名',
    status          TINYINT      DEFAULT 1 COMMENT '状态：1在养、2已出栏、3已屠宰、4异常死亡/淘汰',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    update_time     DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_ear_tag (ear_tag_no),
    INDEX idx_farm_status (farm_id, status)
) ENGINE=InnoDB COMMENT '生猪个体档案';

-- ==================== 疫苗注射记录表 ====================
CREATE TABLE vaccine_record (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id          BIGINT       NOT NULL COMMENT '关联 pig_individual.id',
    vaccine_name    VARCHAR(64)  NOT NULL COMMENT '疫苗名称：猪瘟活疫苗/口蹄疫O型灭活疫苗/高致病性蓝耳病疫苗',
    batch_no        VARCHAR(32)  NOT NULL COMMENT '疫苗生产批次号',
    manufacturer    VARCHAR(128) COMMENT '疫苗生产厂家',
    inject_time     DATETIME     NOT NULL COMMENT '注射时间',
    dosage          VARCHAR(16)  COMMENT '剂量，如"2ml/头"',
    inject_site     VARCHAR(32)  COMMENT '注射部位：耳后肌肉/颈部肌肉',
    operator        VARCHAR(32)  NOT NULL COMMENT '操作人姓名',
    file_ids        JSON         COMMENT '疫苗瓶身照片/免疫档案扫描件 [文件ID数组]',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_pig (pig_id),
    INDEX idx_time (inject_time)
) ENGINE=InnoDB COMMENT '疫苗注射记录';

-- ==================== 出栏申报表 ====================
CREATE TABLE slaughter_apply (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id              BIGINT       NOT NULL UNIQUE COMMENT '一对一关联 pig_individual.id',
    apply_no            VARCHAR(32)  NOT NULL UNIQUE COMMENT '申报编号：SA+yyyymmdd+4位序号',
    apply_time          DATETIME     NOT NULL COMMENT '申报时间',
    weight_kg           DECIMAL(6,1) COMMENT '出栏体重(kg)',
    target_slaughterhouse VARCHAR(128) COMMENT '目标屠宰场名称及地址',
    approval_status     TINYINT      DEFAULT 0 COMMENT '审批状态：0待审、1通过、2驳回',
    approval_time       DATETIME     COMMENT '审批时间',
    approver            VARCHAR(32)  COMMENT '审批人',
    reject_reason       VARCHAR(256) COMMENT '驳回原因',
    create_time         DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_status (approval_status),
    INDEX idx_apply_no (apply_no)
) ENGINE=InnoDB COMMENT '出栏申报';

-- ==================== 产地检疫证明表 ====================
CREATE TABLE quarantine_certificate (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id          BIGINT       NOT NULL COMMENT '关联 pig_individual.id',
    cert_no         VARCHAR(32)  NOT NULL UNIQUE COMMENT '检疫证明编号',
    issue_org       VARCHAR(128) NOT NULL COMMENT '签发机构全称',
    issue_time      DATETIME     NOT NULL COMMENT '签发时间',
    valid_until     DATE         COMMENT '有效期至（通常出证后7天）',
    inspector       VARCHAR(32)  COMMENT '官方兽医姓名',
    cert_type       VARCHAR(32)  DEFAULT '产地检疫' COMMENT '证明类型',
    file_id         VARCHAR(64)  NOT NULL COMMENT '检疫证原件扫描件文件ID',
    ca_signature    TEXT         NOT NULL COMMENT '签发机构CA数字签名（SM2签名值Base64编码）',
    content_hash    CHAR(64)     NOT NULL COMMENT '证照内容+签名的SHA-256哈希',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_cert_no (cert_no),
    INDEX idx_pig (pig_id)
) ENGINE=InnoDB COMMENT '产地检疫证明';

-- ==================== 养殖场表 ====================
CREATE TABLE farm (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    farm_name       VARCHAR(128) NOT NULL COMMENT '养殖场名称',
    license_no      VARCHAR(32)  NOT NULL COMMENT '养殖许可证编号',
    address         VARCHAR(256) COMMENT '地址',
    contact_person  VARCHAR(32)  COMMENT '联系人',
    contact_phone   VARCHAR(16)  COMMENT '联系电话',
    scale           INT          COMMENT '养殖规模（存栏头数）',
    status          TINYINT      DEFAULT 1 COMMENT '1正常经营、0停业',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB COMMENT '养殖场';
```

#### 3.3.2 屠宰检疫库 (db_slaughter)

```sql
-- ==================== 入场查验表 ====================
CREATE TABLE entry_inspection (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id          BIGINT       NOT NULL COMMENT '关联 pig_individual.id',
    arrive_time     DATETIME     NOT NULL COMMENT '到厂时间',
    vehicle_no      VARCHAR(16)  COMMENT '运输车辆牌照号',
    health_check    TINYINT      NOT NULL COMMENT '临床健康检查：1通过、0异常',
    cert_verified   TINYINT      NOT NULL COMMENT '产地检疫证核验：1通过、0异常',
    abnormal_note   VARCHAR(512) COMMENT '异常情况详细说明',
    inspector       VARCHAR(32)  NOT NULL COMMENT '查验人姓名',
    file_ids        JSON         COMMENT '入场查验照片/视频截图',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_pig (pig_id),
    INDEX idx_arrive_time (arrive_time)
) ENGINE=InnoDB COMMENT '入场查验记录';

-- ==================== 屠宰检验表 ====================
CREATE TABLE slaughter_inspection (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id          BIGINT       NOT NULL COMMENT '关联 pig_individual.id',
    inspect_type    TINYINT      NOT NULL COMMENT '检验类型：1宰前检验、2宰后检验',
    inspect_time    DATETIME     NOT NULL COMMENT '检验时间',
    organ_check     JSON         COMMENT '脏器检查明细 {"心脏":"正常","肝脏":"正常","肺脏":"异常:充血水肿","肾脏":"正常","淋巴结":"正常"}',
    result          TINYINT      NOT NULL COMMENT '检验结果：1合格、0不合格',
    issue_desc      VARCHAR(512) COMMENT '不合格项描述（不合格时必填）',
    disposal        VARCHAR(128) COMMENT '不合格品处理方式：无害化处理/销毁/高温处理',
    veterinary      VARCHAR(32)  NOT NULL COMMENT '官方兽医姓名',
    license_no      VARCHAR(32)  COMMENT '官方兽医执业证号',
    e_signature     TEXT         COMMENT '官方兽医电子签章（SM2签名）',
    file_ids        JSON         COMMENT '检验照片/不合格部位特写/报告扫描件',
    content_hash    CHAR(64)     COMMENT '检验报告SHA-256哈希（用于上链）',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_pig_type (pig_id, inspect_type),
    INDEX idx_result (result)
) ENGINE=InnoDB COMMENT '屠宰检验（宰前+宰后）';

-- ==================== 瘦肉精检测表 ====================
CREATE TABLE ractopamine_test (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    pig_id          BIGINT       NOT NULL COMMENT '关联 pig_individual.id',
    test_time       DATETIME     NOT NULL COMMENT '检测时间',
    test_method     VARCHAR(32)  NOT NULL COMMENT '检测方法：胶体金试纸条法/ELISA/LC-MS/MS',
    test_target     VARCHAR(64)  DEFAULT '盐酸克伦特罗+莱克多巴胺+沙丁胺醇' COMMENT '检测目标物',
    sample_part     VARCHAR(32)  COMMENT '采样部位：尿液/肌肉组织/肝脏',
    result          TINYINT      NOT NULL COMMENT '检测结果：1阴性(合格)、0阳性(不合格)',
    detection_limit VARCHAR(16)  COMMENT '检出限，如"0.5μg/kg"',
    operator        VARCHAR(32)  NOT NULL COMMENT '检测操作人',
    file_ids        JSON         COMMENT '检测试纸条照片/检测报告',
    create_time     DATETIME     DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_pig (pig_id),

### 4.3 存证点与上链时机

| 序号 | 存证点 | 触发条件 | 存证内容 | 来源表 |
|------|--------|----------|----------|--------|
| 1 | 产地检疫 | 检疫证签发提交 | `cert_no` + `issue_org` + `ca_signature` + 证照哈希 | `quarantine_certificate` |
| 2 | 屠宰双检 | 宰后检验+瘦肉精检测均合格+盖章完成 | 双检报告哈希 + 兽医电子签章 | `slaughter_inspection` |
| 3 | 批次分割 | 每次分割操作保存时 | `batch_no` + `parent_batch_no` + `product_name` + `weight` + 内容哈希 | `split_batch` |
| 4 | 门店签收 | 签收人完成电子签名 | `transport_no` + `store_id` + 签收哈希 + 签名 | `store_receipt` |
| 5 | 销售激活 | 产品首次扫码 | `qr_code` + `batch_no` + `activate_time` | `retail_sale` |
| 6 | 召回发布 | 召回令状态设为"已发布" | `recall_no` + 召回范围哈希 + 原因摘要 | `recall_order` |

### 4.4 异步上链流程

```
  业务服务                        RabbitMQ                   blockchain-service          FISCO BCOS
     │                               │                              │                       │
     │ 1.写业务表+计算content_hash     │                              │                       │
     │ 2.写blockchain_record(待确认)    │                              │                       │
     │                               │                              │                       │
     │ 3.发送上链消息                  │                              │                       │
     │ ─────── ChainTxMessage ──────→│                              │                       │
     │ 4.返回给用户(不等待)            │                              │                       │
     │                               │  5.消费消息                   │                       │
     │                               │ ─────────────→                │                       │
     │                               │                               │  6.调用智能合约         │
     │                               │                               │ ─────── tx ──────────→│
     │                               │                               │ ←── tx_hash+block ────│
     │                               │                               │                       │
     │                               │                               │ 7.更新blockchain_record │
     │                               │                               │ (已上链/失败)            │
     │                               │                               │                       │
     │                               │  ←── 失败时写入死信队列 ──────│                       │
     │                               │                               │                       │
     │  8.定时Job扫描待确认超时记录      │                               │                       │
     │  → 重新发送上链消息              │                               │                       │

## 七、安全性设计

| 维度 | 措施 | 实现位置 |
|------|------|---------|
| 传输安全 | 全站HTTPS；内网服务间TLS加密通信 | Nginx + Gateway |
| 身份认证 | JWT Token（有效期2h）+ Refresh Token（有效期7d）；Token黑名单存Redis | auth-service |
| 密码存储 | SM3国密哈希 + 随机盐值，禁止明文存储 | auth-service |
| 权限控制 | RBAC模型；6种角色（养殖/屠宰/配送/零售/监管/管理员）；按角色控制菜单、按钮、API、数据可见范围 | Gateway + 各业务服务AOP切面 |
| 操作审计 | 关键操作记录日志：操作人+时间+IP+内容+结果 | AOP切面统一切入 |
| 数据签名 | 机构CA证书 + SM2数字签名；检疫证明、检验报告、盖章记录均需电子签章 | breeding/slaughter |
| 数据完整性 | 规范化字符串拼接顺序，统一SHA-256；消费者可一键对比链上哈希 | 全服务 |
| 防篡改策略 | 修改不覆盖链上记录 → 追加新版本 → 链上存新旧哈希关联 | blockchain-service |
| 文件安全 | 上传白名单（jpg/jpeg/png/pdf/mp4）；大小限制（图片≤10MB、视频≤50MB）；SHA-256去重 | file-service |
| 防重放攻击 | 每次写链操作携带自增nonce（存于合约mapping），合约校验 | 智能合约层 |
| SQL注入防护 | 全部MyBatis参数化查询（`#{param}`），禁止字符串拼接SQL | DAO层 |
| 接口限流 | Gateway层按用户+接口维度令牌桶限流 | Gateway |
| 国密合规 | 哈希：SM3；签名：SM2 | 全局 |

## 九、关键技术难点与解决方案

| 难点 | 风险等级 | 解决方案 |
|------|---------|---------|
| **双链适配**（FISCO BCOS / Fabric） | 高 | blockchain-service 内部使用**适配器模式**。定义 `BlockchainAdapter` 统一接口，分别实现 `FiscoBcosAdapter`（调用 Solidity 合约）和 `FabricAdapter`（调用 Chaincode）。通过配置 `blockchain.type=fisco/fabric` 切换 |
| **批次拆分树状结构递归查询** | 中 | 利用 MySQL 8.0 **CTE（递归公共表表达式）**：`WITH RECURSIVE split_tree AS (...)` |
| **区块链交易延迟**（通常需2-5秒确认） | 中 | 采用**异步上链**模式：业务写库 → 写 blockchain_record(待确认) → 发MQ → 返回给用户。blockchain-service消费消息执行上链，确认后回写状态。前端显示"链上确认中…"然后"已上链✅" |
| **上链失败补偿** | 中 | 消息消费失败3次后进入**死信队列**；定时 Job（每5分钟）扫描 blockchain_record 中 status=待确认 且超过10分钟的记录，重新投递；最终无法自动恢复的记录标记为"人工补录"，通知管理员 |
| **文件哈希与链上一致性** | 高 | file-service 在上传文件时**即时计算** SHA-256 并返回；各业务服务上链时**直接使用该哈希**，不二次计算。所有存证内容的规范化字符串拼接顺序在 `CanonicalStringBuilder` 工具类中统一实现 |
| **大模型生成模拟物流轨迹** | 低（Demo） | 在 `DataInitRunner` 中：构造 Prompt 模板 → 调用 LLM API → 解析返回的 JSON → 批量写入 `temperature_log` 表 |
| **Demo 数据初始化** | 低 | 编写 `DemoDataInitializer`，检测 `spring.profiles.active=demo` 时自动执行：插入养殖场→生猪→疫苗→检疫证→屠宰→分割→运输→温度→签收→销售全链路模拟数据 |
| **分布式事务一致性** | 中 | 业务写库与上链采用**最终一致性**而非强一致性。业务表写入成功即返回，上链异步补充 |
