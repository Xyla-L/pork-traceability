# 自动录入（设备接入层）验证指南

> 适用范围：B 档自动化录入 —— RFID 闸口、瘦肉精检测仪、温控探头、POS 收银机、签收 PDA 五类设备
> 上报的数据，能否自动写入五张业务表并正确标记来源 `source=DEVICE`。
>
> 没有真机也能完整验证：下面四种方式由浅入深，**方式一 + 方式二** 已足够给评审/客户演示。

---

## 0. 验证前检查（30 秒）

```bash
cd backend && docker compose ps          # 期望：全部 healthy
curl http://localhost/health             # 期望：ok
```

若刚重启过 Docker，请等 1~2 分钟再验证。**注意**：`docker compose` 中业务服务对 Nacos 的依赖
必须是 `condition: service_healthy`（见 `docs/后端设计文档.md` 8.2「启动依赖」），
否则启动期会出现「登录报服务器内部错误」——那是服务尚未就绪，不是功能故障。

自检方法：

```bash
docker inspect (docker ps -aq) --format "{{.Name}} restarts={{.RestartCount}}"
# 期望：所有服务 restarts=0；出现 1~2 说明踩到了启动竞态
```

## 方式一：一键验收脚本（17 用例，最推荐）

用模拟器把「设备那一端」假造出来，跑完全部关键用例并直接给出通过/失败结论。

```bash
cd <项目根目录>
node scripts/test/ingest-acceptance-test.mjs
```

期望输出结尾：

```
结果：12/12 通过
```

覆盖的 12 个用例（判定标准）：

| # | 用例 | 验证的是什么 |
|---|---|---|
| 1 | 设备密钥鉴权 | 错误密钥被拒（`code=2001`），设备不能随便写库 |
| 2 | 幂等 | 同一 `bizKey` 连推 3 次，业务表只新增 **1** 条 |
| 3 | 脏数据不入库 | `-999℃` / `abc` 被拒，业务表新增 0 条 |
| 4 | 异常温度保留 | 超区间温度照常入账并标 `is_abnormal=1`（异常值永不丢弃） |
| 5 | 高频降采样 | 非异常值间隔过密 → `status=4` 丢弃但留档 |
| 6 | 仪器未出结果 | 瘦肉精只推耳标不推结果 → 拒绝（**不得默认阴性**） |
| 6.1 | 瘦肉精正常入账 | 出结果后 `status=2`，`ractopamine_test.source=DEVICE` |
| 7 | 降级可用 | 设备通道异常不影响人工录入入口 |
| 8 | 入场查验卡关 | 检疫证核验未过 → 转人工，业务表新增 0 条 |
| 8.1 | 人工确认放行 | 人工 `approve` 后写入，`source=DEVICE` |
| 9 | 门店收银 | POS 扫码 → 销售记录 `source=DEVICE` 且已售出 |
| 10 | 门店签收 | PDA 签收 → 生成签收单，运单推进到「已签收」 |

常用参数：

```bash
# 换网关地址（例如走 nginx 80 端口）
node scripts/test/ingest-acceptance-test.mjs --base http://localhost/api/v1

# 演示库没有「运输中」运单时，自动发车一条（会改动演示数据状态）
node scripts/test/ingest-acceptance-test.mjs --auto-depart
```

> 用例 1~7 只做只读断言，不污染演示数据；8~10 会**真实写入**业务表 —— 这正是验收目的：
> 证明设备端确实能写业务表。前置数据缺失的用例记 `SKIP`，不计为失败。

## 方式二：页面可视化演示（最直观，适合给评审/客户看）

登录 <http://localhost> → 左侧菜单 **设备接入 → 接入监控**。

1. 进入页面先看两张表：
   - **设备台账**：10 台已登记设备（温度探头 / RFID / 检测仪 / POS / PDA），各自绑定通道与目标表
   - **待确认队列**：每一条设备上报的处理结果（通道 / 状态 / 原因 / 原始报文）
2. 点 **「模拟设备上报」** 按钮：
   - 选择设备 → 通道自动带出
   - 表单按通道动态变化（温度填温度、签收填签收人……）
   - 不确定填什么就点 **「填充示例值」**，它会从真实业务接口取一条可用的运单号 / 商品码
3. 提交，页面会**当场显示回执**：`status / statusLabel / accepted / targetTable / message`
   - `已入账` → 数据已写入业务表
   - `待人工处理` / `已拒绝` → 未入库，页面会说明原因（这就是"卡关"逻辑在起作用）
4. 换到对应业务页面确认落库效果，找 **「数据来源」列**：
   | 通道 | 去哪个页面看 |
   |---|---|
   | 冷链温度 | 分割配送 → 冷链运输 → 温度监控 |
   | 入场查验 | 屠宰管理 → 入场查验 |
   | 瘦肉精 | 屠宰管理 → 瘦肉精检测 |
   | 门店收银 | 销售管理 → 销售记录 |
   | 门店签收 | 分割配送 → 门店签收 |

   **判定标准**：新出现的那条记录，「数据来源」应显示 **设备**（数据库里即 `source=DEVICE`）。

## 方式三：单通道手工验证（模拟器 CLI）

适合逐通道对接联调、或做单点复现。

```bash
# 冒烟：确认接入服务活着、密钥有效、通道登记正确
node scripts/test/device-simulator.mjs ping TEMP-001 dev-key-temp-001

# 各通道单条上报
node scripts/test/device-simulator.mjs temp    TEMP-001   dev-key-temp-001   TR-TEST-0008 6.6
node scripts/test/device-simulator.mjs entry   RFID-001   dev-key-rfid-001   ET-DEMO-0001 BATCH-TEST-01
node scripts/test/device-simulator.mjs racto   READER-001 dev-key-reader-001 ET-DEMO-0001 SAMPLE-001 1 BATCH-TEST-01
node scripts/test/device-simulator.mjs sale    POS-001    dev-key-pos-001    QR-PORK-TEST-0005 38.5 0.75
node scripts/test/device-simulator.mjs receipt PDA-001    dev-key-pda-001    TR-TEST-0016 示范一店 张三

# 连续上报（验证降采样）：20 条、间隔 2 秒
node scripts/test/device-simulator.mjs burst TEMP-001 dev-key-temp-001 TR-TEST-0008 20 2
```

回执照 `status` 判读：

| status | 含义 | 说明 |
|---|---|---|
| 2 | 已入账 | 已写业务表，来源 `DEVICE` |
| 1 | 待人工处理 | 设备不能替人担责（如签收缺签收人），转人工确认 |
| 3 | 已拒绝 | 数据本身不成立（脏值、仪器未出结果、缺批次号） |
| 4 | 已降采样丢弃 | 仅针对非异常值的过高频上报，留档但不入业务表 |

## 方式四：SQL 自证（给"凭什么说自动录入生效了"一个硬证据）

```sql
SELECT 'temperature_log' AS biz_table, source, COUNT(*) AS cnt FROM db_distribution.temperature_log GROUP BY source
UNION ALL SELECT 'store_receipt', source, COUNT(*) FROM db_distribution.store_receipt GROUP BY source
UNION ALL SELECT 'entry_inspection', source, COUNT(*) FROM db_slaughter.entry_inspection GROUP BY source
UNION ALL SELECT 'ractopamine_test', source, COUNT(*) FROM db_slaughter.ractopamine_test GROUP BY source
UNION ALL SELECT 'retail_sale', source, COUNT(*) FROM db_sales.retail_sale GROUP BY source
UNION ALL SELECT 'pig_individual(data_source)', data_source, COUNT(*) FROM db_breeding.pig_individual GROUP BY data_source
UNION ALL SELECT 'vaccine_record', source, COUNT(*) FROM db_breeding.vaccine_record GROUP BY source
UNION ALL SELECT 'slaughter_inspection', source, COUNT(*) FROM db_slaughter.slaughter_inspection GROUP BY source
UNION ALL SELECT 'carcass_stamp', source, COUNT(*) FROM db_slaughter.carcass_stamp GROUP BY source
UNION ALL SELECT 'split_batch', source, COUNT(*) FROM db_distribution.split_batch GROUP BY source;

SELECT status, COUNT(*) FROM db_ingest.ingest_staging GROUP BY status ORDER BY status;
```

执行：

```bash
docker exec -i pork-traceability-mysql-1 mysql -uroot -p<root密码> --default-character-set=utf8mb4 < 上面的SQL文件
```

**2026-09-22 实测结果**（可作为对照基线）：

| 业务表 | MANUAL（人工） | DEVICE（设备） |
|---|---:|---:|
| temperature_log 温度 | 28 | **29** |
| store_receipt 门店签收 | 16 | **5** |
| entry_inspection 入场查验 | 22 | **6** |
| ractopamine_test 瘦肉精 | 21 | **4** |
| retail_sale 零售售出 | 34 | **6** |

接入队列 `ingest_staging` 状态分布：待人工 1 / 已入账 50 / 已拒绝 27 / 降采样 8。

**判定标准**：五张业务表都应有 `DEVICE` 记录；两列并存说明"设备自动录入"与"人工兜底"是**并行通道**，
这正是设计意图（不是设备替代人工）。

## 常见"假失败"（看起来像 bug，其实是正确行为）

| 现象 | 原因 | 结论 |
|---|---|---|
| 入场查验上报后转「待人工」 | 该耳标的检疫证已过有效期（如 QC-TEST-0012 有效期至 2026-09-18） | **正确行为**：核验未过必须卡关。要给生猪配一张未来有效的检疫证才会自动入账 |
| 温度连续上报第 2 条起变成「已降采样」 | 非异常值需满足最小上报间隔（默认 60 秒） | 正常。异常温度不受此限，永不丢弃 |
| 上报返回"下游服务返回异常" | 引用的运单号 / 商品码不存在 | 数据问题，不是链路故障 |
| `ping` 或页面「来源设备」列出现 `å†·è—`、`鍐疯棌` 这类乱码 | 数据被**双重编码**了（补执行 SQL 时走了 PowerShell 管道，见下） | **真问题**，不是显示问题。按 `scripts/test/README.md`「已有库如何补执行 DDL」用 `docker cp` 重写，参考 `backend/init-sql/13-fix-device-encoding.sql` |
| 屠宰某页面接口报"系统内部异常" | 可能是自拟的接口路径不存在（404 被全局异常包装） | 请以 `web-admin/src/api/modules/*.ts` 里的真实路径为准 |

## 真机灰度路径（模拟器全通之后）

1. **单台真机接入** —— 先接一条运输线或一个门禁，跑一周
2. **双写比对** —— 设备自动录入与人工照旧录入并行，统计差异率（最有说服力的验收证据）
3. 差异率达标记后才切「以设备为准」，**人工入口永久保留作兜底**

真机对接所需的上报地址、鉴权头、各通道字段清单、回执语义，见
`scripts/test/README.md` 的「接口约定（给真机对接方）」一节。
