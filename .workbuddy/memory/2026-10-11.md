## 演示页：装车口示例值避开「已有待发车运单」的车牌

**诉求**（承接 10-10 晚的讨论链）：一车在正常情况下同时只有一张待发车运单；撞上会被**并入**（业务上正确），但演示时看不出「建了一张新单」。用户要求「设备模拟上报部分不填充已有待发车订单的车」。

**改动**（仅前端演示页，`web-admin/src/views/ingest/IngestMonitor.vue`）：

**性质澄清**（这轮讨论的结论，值得留档）：
- 并入 vs 拒绝的分界：并入是**记录已发生的现场事实**，拒绝等于把货已经上车的事实丢掉 → 设备侧只能并入/转人工，不能拒绝。

- 真正该加的硬约束在**人工建单**那条路（`POST /distribution/transports` 现在不查同车牌是否已有待发车单），且必须配解绑出口（作废滞留单 / 超窗口），否则僵尸单锁死车。
- 一车沿途送多门店仍是**同一张**多站点运单，不算「两张待发车」。

### 追问：到站刷卡报文里的「卸货门店编码 / 名称」是哪来的（同日，仅回答未改码）

用户问：「车载终端里的卸货门店编码和名称是哪里来的，设备会有这些吗」。查证后的事实：

- **门店只来自报文自报，平台上没有第二个来源**：`ArriveChannelHandler.validate`（`storeId`/`storeName` 都空 → `rejected`）→ `dispatch` 原样透传 → `ingestArrive` 拿它去与该运单站点清单比对（②清单外、③跳站）。**`db_ingest.ingest_device` 没有门店列**（只有 `device_no/device_name/channel/location/vehicle_no/sample_interval_seconds`），连「这台车属于哪家店」都不存在。
- **台账绑定还不一致**：`DEPART-001/003` 绑了 `vehicle_no`（京A·12345 / 京A·12346），而 **`ARRIVE-001` 的 `vehicle_no = NULL`** —— 同一台车的两个角色绑得不一样。`vehicleOf(ctx)` 已支持「报文没给就取台账绑定值」，所以到站终端本来也该绑车牌。
- **历史前提已被推翻**：这条通道原设计对象是「**门店收货区的固定设备**」（设备装在店里，「报出自己在哪家店」才合理）；载体改成**车载终端**后该前提不成立，问题才浮出来。车载终端（T-Box + 读卡头 + 显示）能读的是车牌/卡号/时刻/GPS，门店编码是 ERP/OMS 的主数据，不会下发到车上。
- **关键结论：门店在现流程里是冗余字段** —— ①② 已用车牌把运单锁到**唯一一张未结束**的；站点清单由装车扫码顺序（`transport_item.seq`）定；③④ 要求「必须是当前第一个未到达的站」。所以服务端**本来就能算出**这次到的是哪一站，报文里的门店只起**交叉校验**（防走错店 / 跳站），不是必需。
- **三条出路**：① **服务端推导**（报文只要车牌+卡号+时刻，按「唯一未结束运单 → 第一个未到达站」推；最贴近物理，代价是丢掉「开到清单外」的拦截）② **GPS 电子围栏**（终端报经纬度、门店补坐标；`db_common.sys_org` 现在只有 `name/address/manager/phone`，**没有经纬度**）③ **调度下发 + 到店扫码**（出运单时把站点清单推到车机/司机手机，到店扫门店码；扫码是「确认」不是「选择」，与装车口 `LOAD` 同一纪律；要新增下发通道）。
- **另**：演示页 `DEMO_FIELDS.ARRIVE` 的「卸货门店编码/名称」不是手填，是 `fillSample` 取「该运单当前第一个未到达的站」（`next.storeId/next.storeName`）带出来的 —— 所以演示看起来很自然，正好掩盖了「设备哪来的门店」这个问题。

## 21:30–22:00 收尾复核：修掉快照回归自身的「不可重复 + 删用户数据」缺陷

1. **回归自身不可重复**：`-db.sh` 靠 `BEFORE_SNAP` 比基线，被挤掉的行补不回来 → 第二次跑必红。
2. **更严重：回归在删用户数据**。mjs 头注释写着「绝不动别人已有的行」，实际并没有做到。
