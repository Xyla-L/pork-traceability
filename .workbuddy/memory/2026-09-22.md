## 修复「登录显示服务器内部错误，请稍后重试」

**现象**：用户登录报「服务器内部错误，请稍后重试」（前端 `web-admin/src/utils/request.ts:101`，仅在 HTTP 500 时触发）。

**排查过程**：
1. 直接测 `POST /api/v1/auth/login`（走 nginx:80 与 gateway:8080 两条链路）→ 均 200 且返回 token，接口本身没坏。
2. 查容器：全部 healthy，但 `docker ps` 显示都只 Up 1~2 分钟 —— 整个栈刚被重启过。
3. `docker inspect` 看 `RestartCount`：**除基础设施外所有业务服务都崩过 1~2 次**（gateway=2、ingest=2，其余=1）。
4. gateway/auth 日志实锤：`NacosException: Client not connected, current status:STARTING` → `Application run failed: Failed to start bean 'webServerStartStop'`。

**根因**：`docker-compose.yml` 里业务服务对 Nacos 用的是 `nacos: { condition: service_started }`，只等「容器已创建」不等「服务可用」。Nacos 是 Java 进程，8848(HTTP) 先监听、9848(gRPC) 后监听，业务服务在 9848 未就绪时启动就会注册失败并退出，靠 `restart: unless-stopped` 反复重试。用户报错的时刻正处于该窗口期（16:49~16:50），网关尚未成功启动 → 5xx → 前端提示「服务器内部错误」。几分钟后自行恢复。

**修复**（`backend/docker-compose.yml`）：
1. 给 `nacos` 补 healthcheck，**同时探测 8848 readiness 与 9848 gRPC**：
   `bash -c 'curl -fsS http://localhost:8848/nacos/v1/console/health/readiness >/dev/null && echo > /dev/tcp/localhost/9848'`（nacos 镜像内有 curl/bash，已实测；单独探 8848 不够）
2. 全部 `nacos: { condition: service_started }` → `service_healthy`（6 处：x-app-defaults 锚点 + breeding/slaughter/distribution/sales/blockchain）。

**验收**：`docker compose down && up -d` 后 **16 个容器 RestartCount 全为 0、全 healthy、零崩溃**（修复前 11 个服务各崩 1~2 次）。登录、屠宰四页、设备接入、销售、配送、溯源（真实批次号 SP-TEST-0010）、首页总览、通知、系统用户接口全部 200。

**文档**：`docs/后端设计文档.md` 8.2 后新增「启动依赖（易踩坑，务必按此配置）」小节，含依赖条件表与 Nacos 健康检查写法，并写明验收标准（RestartCount 应为 0）。

## 修复「设备接入页面来源列乱码」——双重编码（mojibake）

**现象**：`/admin/ingest/monitor` 待确认队列的「来源设备」列（列定义 `IngestMonitor.vue:62` `prop="deviceName"`）显示乱码。

**定位过程**（关键：区分「显示问题」和「数据真坏」）：
1. 接口 `ping` 返回 `deviceName = "å†·è—è½¦æ¸©åº¦æŽ¢å¤´ äº¬AÂ·12345"`，而**同一响应里 `message` 是正常中文** → 排除终端/HTTP 编码问题，锁定数据本身。
2. `HEX(device_name)` = `C3A5E280A0C2B7...`，全是 `C3A5`/`C3A8`/`C3A9` 开头 —— `C3A5` 即字符 `å` 的 UTF-8 → 典型双重编码。
3. 长度佐证：TEMP-001 应是 16 字符/33 字节，实际 **33 字符/61 字节**（33 个 UTF-8 字节被当 33 个 Latin-1 字符再存一遍）。
4. 对照 `ingest_staging.error_msg`（Java/JDBC 写入）= `E6B8A9E5BAA6...`（`温度`，正确）→ **JDBC 通道没问题**。
5. 逐表定量扫描 16 张表的中文列（`SUM(HEX(col) LIKE '%C3A5%'...)`）：**仅 `db_ingest.ingest_device` 的 device_name/location/remark 三列 10 行全坏，其余全为 0**。

**根因**：`11-device-ingest.sql` 手动补执行时用了 `Get-Content x.sql | docker exec -i mysql`；PowerShell 5.1 的 `Get-Content` 默认按 ANSI(GBK) 读 UTF-8 文件，字节被破坏后写库。脚本文件本身没问题（由 MySQL entrypoint 初始化时执行是正确的）。

**修复**：`backend/init-sql/13-fix-device-encoding.sql` 重写 10 台设备的三个中文列，用**二进制安全通道**执行：
`docker cp 文件到容器` → `docker exec 容器 sh -c "mysql --default-character-set=utf8mb4 < /tmp/x.sql"`。
验证：`bad_name/bad_loc/bad_remark = 0/0/0`，chars 恢复 16/33；接口返回「冷藏车温度探头 京A·12345」正常。

**预防**：`scripts/test/README.md`「已有库如何补执行 DDL」加了乱码警告 + 正确姿势（docker cp）+ 自检 SQL；并修正了 `docs/自动录入验证指南.md` 里原先误判为「仅显示问题」的那一条。

**工具环境提醒**：PowerShell 输出中文会经 GBK 渲染失真（显示 `鍐疯棌`），判断编码**必须看 CHAR_LENGTH / HEX 等 ASCII 证据**，不要读渲染后的中文。
