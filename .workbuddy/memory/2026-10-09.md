### 行业实际数据（已 web 检索确认）
- 小型定点屠宰场 **日均 100–300 头**，中型 **500–1000 头**，大型 **3000+ 头**；真实案例（湖南麻阳某屠宰厂）年 6 万头 → **日均 164 头**。
- **生猪进厂后须待宰静养 12–24 小时才屠宰** —— 所以「今天杀的猪」来自**昨天或前天的进厂批**，两者是交叉关系，不是同一个分组。

### 五个问题（按严重度）
1. **粒度太粗**：一场一天 = 一个批次，真实规模下是几百到几千头。`pig_ids` JSON 数组撑不住；更糟的是 `ingestBatch` 的追加是「读全量数组 → add → 写回全量」（`new ArrayList<>(batch.getPigIds())` + `updateById`），**O(n²) 且并发下会丢更新**（两条线同时报，后写覆盖先写）。
2. **选的不是生产批**：「屠宰场+屠宰日」是**屠宰台账的日报口径**，不是追溯批。真实的批有四种：进厂批/待宰圈（50–200 头，**瘦肉精抽检与检疫申报按这个批**）、屠宰批（班次/线）、排酸批、出厂批（一车一证）。
3. **跨零点切错**：夜班/凌晨开工很常见，23:50–01:30 的连续屠宰批会被自然日切成两批，早班尾与后班头又会被硬併。
4. **分割批次父子关系被稀释**：分割线扫的是**单头白条的挂钩标签**，天然知道是哪头猪；但现在只报 `parentBatchNo` 挂到「一天的量」上，父子关系等于没有信息量。
5. **待宰 12–24h** 使「进厂批」与「屠宰日」必然错位，用屠宰日归集等于把不同进厂批混在一起。

## 分割批次评审（用户提问，尚未开工）

**问**：分割是不是固定切不同部位？分割操作怎么自动化？

**结论 1 —— 是固定分割（已 web 核实行业口径）**：二分体（白条）→ 六分体（前/中/后各两半）→ 部位肉。中国主流二分体＋六分体，欧美四分体。部位有行业号：1号=颈背肌肉、2号=前腿肉、3号=大排肌肉、4号=后腿肉、5号=里脊（腰花肉），培根=腹部五花。**出肉率刚性**：白条约 75–80kg，红肉 65–70%，其余是骨/脂/皮/副产 —— 「固定」意味着可校验（有清单才查缺项，有占比才对账）。

**结论 2 —— 现状只做到「记录自动化」，不是「分割自动化」**。`ingestSplit` 自动做的四件事：生成 SP 批次号（`BusinessNoGenerator.next("SP")`）、校验 `parentBatchNo` 指向的胴体批次真存在（否则转人工，防断链）、`weightKg>0` 否则 `rejected`、落 `source_ref='SPLIT-001'`/`raw_payload`/`content_hash` + 上链 `SPLIT_BATCH`。人工入口已删（**DEVICE_ONLY**）。

**三个缺口**：
1. **一次上报 = 一条部位记录**。一头猪切 8 个部位要报 8 次、建 8 条互不关联的记录。证据：`parent_batch_id=1` 下并存「二分体」与「猪前腿肉」，无任何字段说明同属一头猪的一次作业。
2. **`product_name` 是自由文本** —— 存量值混写着 `二分体`/`带皮白条`/`猪前腿肉`/`猪后腿肉`/`猪排骨`/`猪五花肉`/`猪里脊`，无部位编码，没法 group by 统计、没法按部位召回。
3. **没有出肉率对账** —— 各部位重量合计对不对得上白条重量，系统不管，少了一块肉无感。
   附带证据：`split_level` 在 `ingestSplit` 里**硬编码 `setSplitLevel(1)`**，而存量数据有 level 2 → 「二分体=level 1 / 部位肉=level 2」的层级概念在模型里从未落地。

**三层改造路径（建议 1+2 一起做，第 3 层属现场硬件）**：
1. 接口从「单条产品」改为「整作业」：报文带 `items[]`（partCode/partName/weightKg/packageCount/packageType）+ `operator`/`lineNo`/`workshop`；系统发**分割作业号**把 N 条记录串成一头猪。
2. **部位字典** `meat_part`（part_code / part_name / segment 前中后 / category 红肉骨脂皮副产 / required）+ `split_batch` 加 `part_code`、`split_job_id`；落库后自动校验 ① 总出肉率是否落在合理区间（约 65–100%，含骨脂）② 必出项是否缺项 —— 异常转人工。
3. 设备侧联动：挂钩标签自动识读（免手扫 `parentBatchNo`）+ 分部位工位秤自带部位码（±5g，取代手输 `productName`）+ 产线 PLC 汇总整作业后一次上报。

## 第 14 轮（17:40–19:50）：装车口 `LOAD` 通道 + 允许分车（运单自动化的第 2 层）

**唯独「装车出场」0 台**；库里**没有车辆备案表、没有司机备案表**；`db_sales` 只有
`retail_sale`/`recall_order`/`expire_warning`，**没有要货单** —— 目的地门店在系统里没有任何上游依据。
结论落成字段级可达性：分割批次 ✅、起运地 ✅、车牌 ⚠️（要加相机）、车型 ⚠️（缺主数据）、

### 关键设计：扫码是「确认」，不是「选择」
`LOAD` 是整个系统里**唯一一条不产生任何业务判定的通道**。车牌识别相机 + 司机实名终端 + 扫码枪

扫到的批次属于哪张计划，就发到那张计划的目的地。三条红线：
① 目的地是决策，设备不许猜（猜错就是货发错店）；② 司机必须实名留痕，不能拿车牌号顶替司机；
③ 自动建单失败**一律转人工**，绝不默认正常。

## 第 15 轮（20:35–21:35）：司机识别改造 —— 主数据 + 刷卡为主、车牌反查为辅（自动化第 3 层）

### 起因：两个追问
用户先问「车牌识别和司机实名在同一个设备上合理吗，还有比实名更简单、机器录入更合理的方式吗」，
再问「那现在应该怎么改」。结论落成两层：

**① 「点位 ≠ 一台设备」。** 相机面朝车道、读卡器要司机伸手、扫码枪在装卸位 —— 安装位置、维护方、
故障模式都不同；把「车」和「人」用设备绑死更错（交接班、临时顶班、一车两人是常态）。
正确做法：**通道粒度 = 业务事件粒度，不必等于物理设备粒度**。上报入口仍是一个 `LOAD` 通道，
报文里用 `vehicleSource` / `driverSource` 分开标来源，相机坏了不影响刷卡照常上报。

**② 「实名」≠「人脸」。** 人脸要司机停车配合、逆光/夜间/口罩都失败、终端最贵，冷链戴手套指纹更不行。
更简单且**机器能自动录**的是 **IC 刷卡**（贴一下自动读卡号），卡在人手上自带最低限度责任 ——
这是卡口/物流园区的通行做法。人脸降级为可选强化档。

京A·12345/张师傅/8801、京A·99999/李四/8802、京B·10086/王五/8803。

## 第 16 轮：设计评审（**只答复、未动代码**）—— 要不要给商家端加「选购」

起因：用户提出给商家端加选购页 → 选购后自动生成运单 → 门店端显示待签收运单号 → 可以不接支付吗。

### 定下的口径（结论，供后续实施遵循）
- **不做选购/订单/商城。** 判据：溯源链只认「已发生的事实 + 能追到的责任人」；订单是**意愿**（没发生）、
  不接支付则**无责任主体**，进了链就是往事实库里掺臆造数据。再则它会造出**第二套「要发什么」的口径**，
  与项目一直守的唯一口径原则冲突。
- **运单的上游是「调度决策」= 发货计划，不是客户订单。** 运单四要素各有出处：货←装车口扫批次标签、
  车←车牌识别+`vehicle` 备案、人←司机刷卡+`driver` 备案、**目的地←`delivery_plan`**（唯一必须由
  「决定」产生的字段，也是订单在这条链上唯一能占的位置，已被计划占住）。四要素齐 → 无订单也闭合。
  出库发运是**必然发生**的事（补货/调拨/铺货都会发车），订单不是链路必经节点。
- **代价（要如实说）**：`delivery_plan.operator` 是内部调度人实名 —— 若业务现实是「门店要货→总部配送」，
  则「门店要过货」这个意愿**无记录**。不影响溯源链完整性，但做不了经营侧统计（要货量/缺货率）。
  这是定位取舍：**只记事实，不记意愿**。
- **真正的缺陷在别处（该补的是这个）**：`store_receipt.receiver` 现在是 **web-admin 内部人员手敲**的姓名
  （`StoreReceipt.vue` placeholder「请输入签收人姓名」）。门店签收是**货权转移**节点，却由**发货方代敲**，
  责任主体失真 —— 与「设备≠人」「人名不得兜底」同一个病。补法：**门店端做「签收台」而不是商城**
  （「我的待签收」列表 + 清点确认），判定口径 `status IN (2,3)` 且无 `store_receipt`。可类比第 15 轮给
  `receipt_source` 加来源（门店自助/内部代录），与 `driver_source` 同构。数据隔离按 `store_id` 绑账号
  （安全边界，必须做）；建议放 mini-app（门店手机拍照签字）。
- **若确实要记「门店要货」**：不新建订单体系，把**「发货计划制单」入口下放给门店** + 加 `plan_source`
  （内部调度/门店自提），可选加「内部确认」才可排车。零新表、零金额、不破唯一口径。
- **若真要商城/订单/结算**：那是 ERP/OMS 的事，接口把「要发货」推成一张发货计划，别长在溯源系统里。

### 追加口径（第 16 轮续）：外部订单怎么进来
现实是**多系统协作**（订单在 ERP/OMS，本系统只管溯源）。所以订单**不该在本系统产生，但可以收进来** ——
这不是加业务模块，而是**再加一条接入通道**（与 TEMPERATURE/ENTRY/LOAD 同机制，差别只在 `source`）。
- **红线：订单 ≠ 计划，订单是计划的一种「来源」。** 链路：`ERP/OMS 订单 → 订单通道 → 发货计划(plan_source=ORDER)
  → 装车口 → 运单`。**运单上游永远是计划，不是订单**（第 16 轮已定，不能因为加了订单通道就退回「下单即运单」）。
  `plan_source ∈ {MANUAL, ORDER}`，照搬 distribution 现有的 `SOURCE_MANUAL/SOURCE_DEVICE` 口径。
- **订单不能 1:1 直通计划**：`delivery_plan.store_id` 单值 + `store_receipt` 是 `uk_transport` 唯一 →
  **一张运单只能对一家门店**；而多店可拼一车、一单可分多车。故订单→计划之间必须有一层**归并/排车决定**
  （这是唯一需要动结构的地方：要么计划支持一车多店，要么订单先聚成配送批次再排车）。
- **订单通道只收 4 个字段**：订单号+下单方、目的地门店（须映射 `sys_org.type=retail`，查不到转人工）、
  要什么货（部位+数量）、期望到货时间。**金额/优惠/合同/支付状态一个都不收** —— 这就是「不涉及支付」的落地方式：
  不是事后不接支付，而是**字段层面就不接收**。
- **与其它通道的本质差别（必须写进 handler 注释）**：其它 handler 落的是「已经发生的事实」，订单通道落的是
  **「待排车的计划」（决策还没做完）**。不写清，后人会照抄「直接落库」把「待排车」当成「已排车」。
- **真正的坑**：订单里是「20kg 大排」，而 `split_batch` 是实物批次（18.6+12.4）；`delivery_plan_item` 现在
  直接挂 `split_batch_id` = **现在是「人挑批次」**。订单自动转计划后，「按部位+重量 → 具体批次」必须有人确认或
  写分配规则，**这层比通道本身工作量大**。
- **幂等**：同一 `order_no` 重复推送不得重复建计划（ERP 重推是常态）。
- **兜底**：补货/调拨/铺货没有订单，`plan_source=MANUAL` 的人工建计划入口**永远保留**。

### 本轮自查揪出的两个真实缺陷（都是自己 review 出来的，不是回归报的）

2. **机构服务不可用会让外部系统删单**：`OrgClient` 抛 `REMOTE_CALL_ERROR` → 原写法一路抛到接入层 `process()`，

   **回执语义要点**：`written=false + retryable=true` 才是转人工；`retryable=false` = 「数据本身不成立、不要重推」，
   **订单重推是常态，宁可多收一条待人工，也不能让真实订单在接入层消失。**

### ⚠️ 构建快照事故（本轮最值得记的教训）
第一次跑回归 **HTTP 29/1**，唯一失败的是「订购重量为 0 → 拒绝」：它**没被拦截**，
反而入账并建出计划 52（一张 0 明细的空计划）；而 B 组其余三条（缺订单号/缺门店/缺明细）都正确拒绝了。
- **根因不是代码，是镜像没带上新代码。** 那三处「零/负重量」防御我是在**构建启动之后**才写进去的
  （源码 mtime 22:16:43~22:16:53，构建 22:16:33 启动 —— 晚 10~20 秒，Docker 的 `COPY` 已经执行完），
  编译进镜像的是**旧快照**。
- **铁证是字节码**：`OrderChannelHandler.class` 里 `'重量必须大于 0'` 出现 **0 次**，
  而同在 `validate` 里的 `'缺少重量'`/`'缺少订单号'`/`'缺少货物明细'` 都在。
  **正好解释「为什么只有一条失败」**：另三条走的是早退分支，只有它必须走被漏掉的那个 items 循环。
- **排查手法（可复用）**：`docker cp <容器>:/app/app.jar` 拷出 → Python `zipfile` 读 class 常量池比对关键字串出现次数。
  **能确凿区分「代码错」和「镜像旧」**，比反复重跑回归快得多。
- **纪律**：改完代码**再启动构建**；若构建已开跑又改了源码，**必须重建**。
  用 `find . -name '*.java' -newermt '<构建启动时刻>'` 一条命令就能找出「构建后被改的文件」。
- 重建（`--no-cache ingest-service distribution-service`）后 **HTTP 30/0 + 落库 22/0** 全绿。
