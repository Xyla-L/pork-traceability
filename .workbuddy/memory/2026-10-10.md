## 第 18 轮（咨询，**只答复、未动代码**）：发车设备化 / 一车多目的地 / 温度定频

用户五个问题：① 现在发车是人工的吗；② 车上放设备、有待发车运单时刷卡发车行不行；
③ 小订单也单独出一个运单？④ 现实是一车装满且多目的地，怎么解决、是否超出范围；
⑤ 温度探头是不是该固定间隔自动打卡。**逐个回答。**

### 先核的实现现状（都是查过的，不是推测）
- **发车是纯人工**：`TransportMonitor.vue` 点「立即发车」（`el-popconfirm`）→ `distributionApi.departTransport`
  → 运单 `status` 1(待发车)→2(运输中) + 写 `depart_time`。**装车那一步已自动**（`LOAD` 通道自动建单，
  停在 `status=1`），**自动化在最后一步断了**。
- **温度链路已通大半**：`temperature_log.transport_id`（温度已挂运单）、`record_method=DEVICE`、
  `source=DEVICE`；探头已登记（`TEMP-001 冷藏车温度探头 京A·12345`、`TEMP-003 …京A·12346`）。
  `TemperatureChannelHandler` 已有：**非异常值按最小间隔 60 秒降采样**（`ingest.temperature.min-interval-seconds`）、
  **补传的历史时间戳不参与降采样**（`current.isBefore(last.reportTime)`）、**异常值永留**、
  物理合理性区间 [-60,60] 挡脏数据。**不校验运单状态**（装车前预冷也能报）。
- **一车一店是硬约束**：`cold_chain_transport.destination` varchar(256) **单值**；
  `store_receipt` 有 `UNIQUE KEY uk_transport(transport_id)`（一运单一条签收）；`delivery_plan.store_id` 单值。
- **载重已有主数据**：`vehicle.load_capacity_kg`（5000 / 8000 / 3000，`29-driver-vehicle-master.sql` 建的）。
- `transport_item` 已支持一车多批。

### 定下的口径（供后续实施遵循）
- **② 发车设备化：可行且自然** —— 装车口已完成 90%。机制：车载终端 `device_no` 代表车
  （同 `TEMP-001` 绑车牌的做法）→ 刷卡 → 拿设备号反查车牌 → 找该车牌下 `status=1` 的运单 → 推进「运输中」。
  **设备只报「我（某车）发车了」，运单号由系统倒查**（同「扫码是确认不是选择」）。
  发车是**物理事实**（道闸抬杆/地磅出场/GPS 出围栏/点火）且**不产生业务判定**，比人点按钮可靠。
  **前置条件**：设备台账必须能把「车载终端 ↔ 车牌」**结构化对上** —— 现在 `ingest_device.location`
  是「一号冷藏车车厢」这种自然语言，要设备化发车得先让绑定可查（`device_no` 带车牌 / 加列 / 加绑定表）。
- **③④ 一车多目的地 —— 这条判据线是本轮的核心产出**：
  > **凡是「已经发生、有现场设备或第三方单据作证」的 → 在范围内；
  > 凡是「还没发生的选择、要算法来优化」的 → 超出范围。**
  - **「哪几家店拼一趟车、怎么排线、先送谁」= 决策 → 超出范围**（TMS 的活，本系统也无路线/时效/
    装载优化数据源；硬做 = 造第二个真相，同「订单」那次）。
  - **「这趟车实际送了哪几家、每家的温度/数量/签收」= 事实 → 必须在范围内，而现在缺这一半**：
    一趟车送 4 家店、后两家超温，单值 `destination` + 单条签收**表达不了**，溯源链上就是空白。
  - 正确形态：**运单粒度从「一次送货」上移到「一个车次」**，一个车次挂 N 家门店。要放开三处：
    `destination` 单值→多目的地；`store_receipt.uk_transport` → `uk(transport_id, store_id)`；
    `delivery_plan.store_id` → 允许一个车次含多张计划。
  - **「谁来拼」与订单同构**：由人的决策或外部 TMS 推入，系统只接收并留痕，**不做拼车算法**。
    （即第 16 轮 `ORDER` 通道意义的延伸。）
  - **超载**：装车时算「已装明细总重 vs `load_capacity_kg`」提示；**超了拦**（既成事实的违规，
    同瘦肉精那种硬判据），**绝不自动凑满一车**（那是决策）。
  - 结论一句话：**「怎么拼」不做；「拼成什么样、送到了没、温度对不对」必须做，现在做不了。**
- **⑤ 温度定频：该做在设备端，不是系统端**。不能系统轮询（车在移动、会进隧道/地库，网络不稳必丢点）；
  正确是**探头定频采样 → 本地缓存 → 联网按真实采样时间补传**。人工记的温度**没有证据力**（事后可改）。
  **真正该补的是「断档检测」**：现在只判单点越界（`is_abnormal`），**没判断档** ——
  15:00 报一条、17:30 才报下一条，中间 2.5 小时空白，系统会显示「温度正常」，
  **这比温度超标更危险**（超了至少看得见，空白是假装有数据）。
  建议：① 探头定频（30 秒~1 分钟采样，5 分钟入库，已有 60 秒降采样兜底）；
  ② **把「采样间隔」声明成设备属性**（写进设备台账/接入协议），系统据它判「到上一条是否超时」；
  ③ 超时 → 曲线标**「区间未采集」**，不用直线连过去装作连续。
  细节：温度上报不校验运单状态（预冷也能报，是好事），但落在发车前的记录**展示时要与「在途温度」分开**，
  否则曲线时间基准会乱。

### 追问「一车多目的地为什么做不了」—— 把改动面钉死（查库实测，非推测）
口径澄清：**不是「做不了」，是「没做」+「不能顺手做」** —— 动的是**数据模型粒度**，不是加字段。
四层各写死一个「1」：
1. `delivery_plan.store_id bigint NOT NULL`（+ 表注释「一个目的地+一个车次」）→ 一计划一店；
2. `cold_chain_transport.destination varchar(256)` 单值 + `split_batch_id bigint NOT NULL`（主批次，第 14 轮为兼容存量 34 条运单保留）→ 一行运单一个目的地；
3. `store_receipt UNIQUE KEY uk_transport (transport_id)` ← **最硬的一条**，一运单只能一条签收 ⇒ 只能对一家门店确认货权转移；
4. **隐性第 4 处**：`transport_item`（transport_id/split_batch_id/batch_no/weight_kg）**只说「货在这辆车上」，不说「在哪一站卸下」** —— 多站点时货物门店归属只能绕道 `delivery_plan_item.plan_id → delivery_plan.store_id` 反查，不是装载记录自身的属性。

**要真做的改动面**（清单化，供后续排期）：
- 运单粒度「一次送货」→「一个车次」；`destination` 降级为**首站/主目的地**（兼容存量 34 条）；
- 新增**车次-站点明细**（或用 `store_receipt` 一格一店）；`uk_transport` → `uk(transport_id, store_id)`；
- `transport_item` 补**卸货门店**字段（否则「这批肉发去哪家」在装载层没有答案）；
- 一车次聚合多张计划（计划本身仍**一店一计划**，由车次聚合，不改计划语义）；
- 连带面：`ReceiptChannelHandler` 签收通道、`StoreReceipt.vue` 签收页（现在收货人手敲、运单号单值）、运单详情、`verify-load` 系列回归、追溯链查询；
- 温度不用改：车厢温度是**整车的**（`temperature_log.transport_id` 单值合理），但「各站到店温度」`store_receipt.temp_value` 要能一站一条。
- 存量风险：34 条运单 + 34 条签收记录全是单值，改唯一键必须同时兼容旧数据。
- **范围判断不变**：「拼成什么样（车次含哪几家、顺序、各站卸了什么）」= 事实 → 该做；「怎么拼」= 决策 → 不做。

### 追问二「让屠宰场先拼车、系统接结果，合理吗 / 现实可行吗 / 接什么设备 / 怎么改」（**只答复，未动代码**）
- **口径澄清**：「超不超」要拆成**规划**（算法：谁跟谁拼、怎么排线 → 本系统零数据源，确实超）与**记录**（这车装了哪几批、按什么顺序送了哪几家 → 事实留痕，不超）。
  用户提议 = 「不在这里做规划，但在别处做完后**在这里接结果**」→ **恰好落在我上轮划的边界内，比我上轮的「不做」更主动**（承认这个决策总要有人做，只是不该由溯源系统做）。
- **三个结构后果（必须点破）**：
  1. **主链路变了**：`delivery_plan` 从「待排车的决策单」**降级为需求池**；运单**不再由计划生成，而由「车次」生成**。链路：订单 → 计划(需求池) → [外部 TMS 排车] → 车次单 → 运单。
  2. **必须新增「出向」**：系统现在**只有入向**（设备报进来）。TMS 要拼车就得先拿到「有哪些货要发、发去哪」→ 要么它自己从 ERP 取订单，要么**本系统把需求池推给它**。这是**双向对接，比 ORDER 通道（单向入）多一个方向**。
  3. **采信 ≠ 免检**：车次单里的货必须自己复核「真的可发运（未被 `transport_item` 引用、未被待发货计划占用）、一车次内不重复、一票货不落两个车次」。
- **现实可行性：分两类客户**。有 TMS/WMS 的连锁商超/大型配送中心 → 可接，但**是少数**；**中小屠宰场（中国绝大多数）没有系统可接**（调度靠白板/微信群/经验）。
  现实常态是**车次「装出来的」而不是「规划出来的」**：装满就走、走到哪家卸哪家，站点顺序司机现场定、中途会改。
  ⇒ **不能把「接 TMS」当唯一路径**，否则系统只服务大客户。正确形态：**「车次」这个实体要来源无关**（TMS / 装车口 / 司机端都能产出），同「设备 ≠ 人」「点位 ≠ 一台设备」是同一种解耦。
- **设备：接入侧一个新设备都不加**。TMS 那一路是系统对系统（HTTP/文件/消息），台账登记虚拟终端即可（类比 `ORDER-TERM-001`）；
  装车口那一路**不动现有 `LOADER-001` 三件套**（相机+刷卡+扫码枪）—— 多站最省事的做法是**「按站装车」**：先装 A 店扫一遍、再装 B 店，**扫码顺序天然就是站点分组**；最多补**标签打印机**。
  **不需要** GPS / 路线规划终端 / 地磅（那是 TMS 的事，不是溯源的事）。
- **系统怎么改（三层）**：
  - **接入层（轻）**：第 17 条通道，报文 `{vehicleNo, driverName, stops:[{storeId, batchNos[]}]}`，机制照 ORDER/LOAD 抄一遍，接入层 100% 现成。
  - **业务层（重）**：新 `transport_trip` + `transport_stop`；`transport_item` 补**卸货门店**；`store_receipt.uk_transport` → `uk(transport_id, store_id)`；`delivery_plan` 降级为需求池。
    这就是上轮标的「独立议题」，与本提议**是同一件事的两半**（提议解决「谁产出拼车结果」，模型改动解决「结果怎么存」）。
  - **校验层（最易忽略）**：**系统没有时效判据 → 接了车次单也验不了好坏**。实测：全后端零个「路线/站点/停靠顺序」概念（唯一 `routes:` 是 gateway 路由），`ingest` 配置只有温度区间 `[-18,0]` 与降采样间隔。
    接收「计划 15:00 到店」只能说「记下了」，不能说「这安排对不对」。⇒ **接的时候要连最小依据一起收**：至少 `planned_depart`/`planned_arrive`（`delivery_plan` 与 `cold_chain_transport` **两列都已有**），还差「谁排的、依据什么」。否则车次单是**不可校验的黑箱** —— 溯源链上只是「存在过」，不是「可追溯」。
- **两条不让步的底线**：① 车次单的货必须自检可发运/不重复；② 路线临时改了（绕路/加点）→ 走**签收反向确认**，**不回头改车次单**（计划是计划、事实是事实，两份都留 —— 同「设备重推命中已占用 → 回既有批次，不篡改已有记录」）。

### 追问三「按实际情况要怎么改」—— 定下的最小改造清单（**只答复，未动代码**）
**核心结论：不需要新建车次表，也不需要刻意建 TRIP 通道。** 现实里中小屠宰场没有 TMS 可接，而**车次的真相就在装车口的扫码枪里** —— 扫到的每一批货本来就带着门店归属（通过 `delivery_plan`），**一车多店是「扫出来的」，不是「规划出来的」**。
`cold_chain_transport` 本身就映射现实里的「车次」，`store_receipt` 就是「每站签收单」，`transport_item` 按门店聚合就是站点清单。**现有数据模型早就留好了位置**（`store_receipt.store_id` 列 + `idx_store` 索引本来就在，`ReceiptChannelHandler` 报文里**早就在传 `storeId`**），挡路的只是几处「单值假设」。

**唯一真正的拦路石**（`DistributionDeviceIngestService.ingestLoad` 第 ④ 步）：
```java
if (planIds.size() > 1) return manual("…一车只能发一张计划的货，请人工核对装车清单是否装混");
```
而 `generateTransportFromPlan(id, splitBatchIds, site)` 只接受**一张计划**、`transport.setDestination(plan.getStoreName())` 单值 —— 「一车一计划」是从这里来的。

**改动清单（按实际重要性）**：
- **A. `transport_item` 加 3 列**：`store_id` / `store_name` / `seq`（第几站）。**不需要新建站点表** —— `SELECT DISTINCT seq, store_id … WHERE transport_id=?` 就是站点清单。
- **B. `store_receipt` 唯一键**：`uk_transport(transport_id)` → `uk_transport_store(transport_id, store_id)`。存量 34 条不受影响（原本一单只有一店，新键仍唯一）。连带改 `DistributionServiceImpl.saveReceipt` 的幂等判定（现按 `transport_id` 单值，line ≈895）。
- **C. `ingestLoad` 第 ④ 步**：「分属多张计划 → 转人工」改为「按计划分组 → 得 N 家门店 → 每组建 `transport_item`（带 store_id/seq）→ 仍只建**一张运单**」。**红线没破**：每批的归属仍是确定的（所属计划的目的地），**没有一处是猜的**；转人工边界收窄为「批次不属于任何计划」。
- **D. `generateTransportFromPlan` 扩展**（改动最大）：入口从「一张计划 + 批次」变为「多张计划 + 按门店分组的批次」。逐张推进计划状态（A 发完→2、B 有剩→4）；每张计划 `transport_count` 各自 +1（都是同一张运单）；`resolveSiteValue` 的「计划值」在多计划时取任一非空、不一致仍拒绝。
- **E. `destination` 不改列、只改语义**：站点 >1 时展示「途经 N 站」，=1 时就是门店名（存量 34 条即此）。
- **F. 前端**：`TransportMonitor.vue` 目的地列 + 站点明细（站点/门店/货量/到达/签收态）；`StoreReceipt.vue` 按 (运单, 门店) 定位。
- **G. 超载拦截（可后置）**：`vehicle.load_capacity_kg`（5000/8000/3000）已有；装车时 `SUM(transport_item.weight_kg) > 载重` → 拒绝。查不到备案不拦（同 `vehicleType` 口径：备案不是准入门槛）。

**明确不做**：不建 `transport_trip`/`transport_stop` 表（运单就是车次）；不做拼车算法/路线规划；不改 `temperature_log`（整车一个温区是合理的）；**不刻意建 `TRIP` 通道**（没客户要接就先不建，真有了照 `ORDER` 抄一条、复用 D 的落地逻辑）。

**作业细节（真实约束）**：「扫码顺序 = 站点顺序」只在**按站装车**时成立。若工人混装 → `seq` 留空，站点顺序按**签收时间**（实际到达顺序）回填 —— 也是事实。建议规范为「后卸的先装」。

**分期**：① A+B+C+D+E+最小前端（装车口扫码自动成立多站车次）；② G + 站点计划时刻；③ 等有客户再接 TMS 车次单。

## 实施：一车多目的地 + 刷卡发车 + 温度断档（同日，用户指令「那就这样改，并且把上面提到的刷卡发车和温度探头定时打卡的那些问题也一起修改」）

**三件事一个批次落地。上轮方案再收一刀**：不建 `transport_trip`/`transport_stop`，不建 `TRIP` 通道 —— 改成「`transport_item` 加三列」，工作量从「重」降到「中」。

### 1) 一车多目的地（多站车次）
- **SQL `init-sql/31-multi-stop-depart-temp.sql`**（幂等，ALTER 前探 `information_schema`）：`transport_item` 加 `store_id`/`store_name`/`seq` + `idx_item_store`，存量回填 `store_name`（自 `cold_chain_transport.destination`）与 `seq=1`；`store_receipt` 删 `uk_transport` 加 `uk_transport_store(transport_id, store_id)`；`cold_chain_transport` 加 `stop_count` 并按明细门店数回填；`ingest_device` 加 `vehicle_no`/`sample_interval_seconds`；`temperature_log` 加 `sample_interval_seconds`/`gap_seconds`/`is_gap` + `idx_gap`。
- **口径只写一份**：`generateTransportFromPlan(id,…)` 改为**委托** `generateTransportFromPlans(List,…)`，不让两条路径各自演化。
- **站点顺序 = 扫码顺序**：`target` 原本按数据库 id 排序会冲掉扫码顺序 → 改为 `want.stream().map(byBatch::get)` 保住调用方顺序；`planSeq` 按 target 顺序分配站点号。
- **`destination` 语义**：>1 站写「途经 N 站：A、B」，=1 站写门店名（存量 34 条语义不变、无需迁移）。
- **签收按 (运单, 门店)**：`createReceipt` 幂等键改 (transportId, storeId)；状态推进改为「明细去重门店数」（`stop_count` 只是展示快照）；**所有站点签完才算已签收**。
- **`transportStops(id)`**（`GET /distribution/transports/{id}/stops`）：按 `store_id`（人工建单无 id 时按 name 兜底）聚合 `transport_item`，关联 `store_receipt` 得 `received/receiptId/receiptTime/receiver`，标 `primary`。

### 2) 刷卡发车（第 16 条通道 `DEPART`）

## 追问：「还需要商家终端吗 + 订单上报了却没在计划列表显示」

### 1) 结论：商家终端仍需要，但它只干一件事 —— 报需求
「一车多店是**扫出来的**，不是规划出来的」定下的是「拼车/路线规划不接」。所以商家终端（对外部而言是 ERP/OMS/商家选购 App）从「拼车算法的输入端」**降级为「需求事实的来源」**：它报「哪家店、要什么部位、多少公斤、什么时候要」，本系统落一张**待发货计划**（车/司机留空）。之后要么人去排车，要么直接装车口扫码倒查计划得到目的地（一次装几家店 = 多站车次）。
**它不是链路必需环节**：没有它，在「冷链运输」页手工「新建计划」（`plan_source=MANUAL`）照样跑，下游完全一样。本系统里也**没有也不需要**「商家终端」这个页面 —— 它是别人的系统，我们只是收单那一端。

## 站点级到达（做法 A）落地：到达粒度从「运单」下沉到「卸货门店」

用户问：司机刷卡发车后计划变「已发运」，但运单和页面还停在「待发车」；发车之后怎么表示到达？一车多批又该怎么确到没到？
答（先只回答，用户拍板「按照 A 来改」）：**到达的粒度是「卸货门店」不是「批次」**。同店多批只到一次，多站车次一站一次 —— 「到了没」问的是车在不在这个卸货点，与车厢里装了几批货无关。做法 A = 站点级到达：新增站点行程表 + ARRIVE 通道 + 运单状态由站点汇总推导。

### 1) 为什么要单开一张表（而不是继续用 `transport_item` 聚合）
站点**清单**确实能从 `transport_item` 按 `store_id` 聚合出来（31 号迁移已确立「不建站点清单表」），但**行程状态**（未到达/已到达/已签收 + 到达时刻）是新事实，装载明细装不下：
- `cold_chain_transport` 只有一个 `arrive_time`（多站装不下）；
- `store_receipt` 是**终态凭证**——只在签收那一刻建行，「到了但还在排队卸货」这个中间态无处安放。
所以：清单仍由 `transport_item` 派生，**状态落 `transport_stop`**。

### 3) 回归过程中抓到并修掉的两个真问题
**缺陷 A（死代码）：到达倒查只认「运输中(2)」，导致「所有站点都已到达」分支永远不可达。**
`ingestArrive` 原来 `eq(status, STATUS_IN_TRANSIT)`。可是三站到齐后 `recomputeTransportStatus` 会把运单推到 **3（待签收）**，此刻设备再报一次到达（外部重推、司机多刷一下）→ 倒查 0 张 → 回「**名下没有运输中的运单**，请先确认该车已完成刷卡发车」。这话把人往「是不是没发车」上带，而真实原因是「本趟已经全部到过了」；同时 `next == null → 所有站点都已到达` 那段**成了死代码**（被新写的回归当场抓到）。
